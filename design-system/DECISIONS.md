   moved to the flat layout and `design-system/nutritime-ai/` was removed. Content is unmodified.

   the tenth. PRD outranks the Plan's example either way.

   `prettier --check` clean. Formatting the eleven generated files was whitespace-only in ten of

   `#EA580C` to `#ea580c`, `#ECFDF5` to `#ecfdf5`, `#E2E8F0` to `#e2e8f0`. Nothing else changed —

### 12.2 `outline: none` — the verdict stands and the reason was invented

§5 rejects the generator's `input:focus { outline: none }`. **The rejection is right and one of its
two reasons is not**, which is a worse artefact than a rejection with no reason at all: `Plan.md`
T-27-03 exists for the recommendation that carries no reason, and this file already records two
items honestly as _"no reason recorded"_. An invented reason is the opposite of that, because the
next reader acts on it.

**What the cell said:** _"Removing the focus ring is the first item under the skill's own CRITICAL
accessibility list and violates PRD §10.5. `focusRing` in `component.ts` is always visible and
3:1."_

**What is true, measured:**

- The skill half **stands.** `SKILL.md`'s row 1 is `Accessibility | CRITICAL` and its Avoid column
  reads _"Removing focus rings, Icon-only buttons without labels"_. First of two, as claimed.
- _"violates PRD §10.5"_ is **false.** §10.5 has four bullets — roles and labels with the
  platform-specific touch targets; text scaling without clipping; _"Color is never the only carrier
  of status"_; and _"Both themes meet WCAG AA contrast where measurable"_. The word **"focus"
  appears nowhere in `PRD.md`**, and neither does "keyboard", "tab order" or "hover". See §12.3.
- _"`focusRing` in `component.ts` is always visible and 3:1"_ is **false, and false in a way that
  matters.** `focusRing` occurs exactly twice in the whole tree — its `ComponentTokens` member and
  the expression that fills it — **both inside `component.ts`.** Nothing consumes it, so nothing
  paints it: a ring with no consumer is not "always visible", it is never visible. The 3:1 figure is
  true of the **colour** `border.focus`, which §3.1 measured at 3.58:1 on the canvas, 3.77 raised
  and 3.49 sunken; the rendered field border uses that same colour. So the number was real and the
  sentence attached it to the wrong object. `component.ts`'s own comment at the `focusRing` group
  now says so, and `focus-indicator.test.ts` holds the measurement.

**The corrected reason, and the Reject stands on all three:**

1. **`outline: none` is not expressible in either realm, so adopting it would mean writing something
   the platforms reject.** React Native 0.86.3 declares only the four `outline*` longhands in
   `ViewStyle` and its `outlineStyle` union is `'solid' | 'dotted' | 'dashed'` — `'none'` is not in
   it (`node_modules/react-native/Libraries/StyleSheet/StyleSheetTypes.d.ts`, the
   `outlineColor`/`outlineOffset`/`outlineStyle`/`outlineWidth` block). react-native-web 0.21.2
   lists `outline` among its `invalidShortforms`
   (`node_modules/react-native-web/dist/exports/StyleSheet/validate.js`), so the CSS shorthand is
   refused there too. Read from the shipped source in both cases, with the versions stated, because
   a comment that explains a library's behaviour has to have opened it (`BRIEF.md` §6.1j). This is
   the same class as §5's rejections of `cursor: pointer` and `backdrop-filter`.
2. **On the web export it would delete the only focus indicator fourteen of the sixteen components
   have.** `FormField.tsx` and `SearchField.tsx` are the only shared components that render a
   focused state; for every other focusable control the user agent's outline is the entire focus
   affordance. Suppressing it leaves a keyboard user with no visible focus anywhere except two text
   fields — which is what the skill's `focus-states` rule (_"Visible focus rings on interactive
   elements (2–4px)"_) forbids, and what §12.1's focus row is Partial about.
3. **The binding requirement is §14.2's checklist, not PRD §10.5.** `Plan.md` §14.2 adopts
   "contrast, **focus**, reduced motion, no emoji icons, responsive breakpoints" as a named gate
   item in every frontend phase, and T-23-07 re-requires it run in full. The _measurable_ part
   reaches PRD §10.5 only through its fourth bullet, which adopts WCAG AA — and 1.4.11 Non-text
   Contrast is an AA criterion that covers component **states**, not only components. That is a real

### 12.3 PRD §10.5 in this file — ten citations, six of them true
