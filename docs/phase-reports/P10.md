## No model anywhere, and that is the point

The safety path - allergen and diet rejection **before** any scoring - is proved end to end through
HTTP before a model exists. When P19 adds one there is a green baseline to compare against rather
than two new variables at once.

`explanationSource` is therefore always `fallback`. Marking it `gemma` would be a lie about where the
prose came from.

## The assertion that matters

A user who declares a peanut allergy gets no peanut-tagged meal **even when every peanut meal is in
their `favoriteMealIds`**, so the +10 previous-like weight cannot buy a rejected meal past the
filter. Tested through the HTTP boundary rather than only in the domain, because that is where a
future refactor would break it.

Also asserted: an allergen present only in the ingredient list with no declared tag is still
rejected, because `hasAllergenConflict` works on effective tags - declared union inferred.

## The fallback explanation cannot outrun the score

Every clause is a `detail` string the scoring policy itself wrote, so the sentence cannot claim
anything the score did not. Reasons are taken in descending points with declaration order as the
tie-break, which makes the same meal always produce the same sentence.

When every policy scored zero it says `"This one fits your preferences."` - the only claim the data
supports. Inventing a reason there would make `explanationSource: 'fallback'` a euphemism.

## Contract details recorded

- **No 503 on this endpoint** (Plan C-04), verified with Ollama pointed at a dead port: still 200,
  every explanation `fallback`. A recommendation is useful without prose, and PRD FR-009 says the
  feature degrades rather than fails.
- **`mealPeriod` is required and the server derives no time.** TSD 5.4: deriving it here as well
  would compute one fact along two paths that can disagree across a minute boundary or a timezone
  read. The client computes it from 4.3 and sends the result.
- **`z.strictObject`, so an extra body field is a 400.** A request body is a contract the client is
  expected to know; a query string is not, which is why the two validate differently.
- **`scoreReasons` are returned** so a score can be checked rather than trusted.

## Known limitations carried forward

- **`_config` is unused** in `recommendationsRouter`. It is threaded now because P19 reads
  `AI_ENABLED`, `OLLAMA_*` and `GENERATION` from it, and adding the parameter later would touch every
  call site. Named with the underscore the lint rule recognises.
- **One test is conditional on the fixture.** The null-nutrient goal assertion runs only if an
  `unavailable` meal reaches the top three; with 53 of 60 records unavailable it does today, but the
  guard means it would pass vacuously if coverage rose. Flagged to the verifier rather than left
  silent.
