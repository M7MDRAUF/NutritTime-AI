## No model anywhere, and that is the point

The safety path - allergen and diet rejection **before** any scoring - is proved end to end through
HTTP before a model exists. When P19 adds one there is a green baseline to compare against rather
than two new variables at once.

`explanationSource` is therefore always `fallback`. Marking it `gemma` would be a lie about where the
prose came from.

## The assertion that matters

A user who declares a peanut allergy gets no peanut-tagged meal **even when every peanut meal is in
their `favoriteMealIds`**, so the +10 previous-like weight cannot buy a rejected meal past the
filter. Tested through the HTTP boundary rather than only in the domain, because that is where a
future refactor would break it.

### A claim this report made before the suite could support it

The first version of this section said _"an allergen present only in the ingredient list with no
declared tag is still rejected."_ **The suite did not show that,** and the test that was supposed to
was unsound in three ways at once:

1. It declared `allergies: ['seafood']` and asserted that no prawn or salmon appeared in the three
   returned meals. Only three come back out of sixty, so "did not appear" is a statement about
   scoring rather than about rejection - the test would have passed with the allergen filter
   deleted outright.
2. `seafood` is not a canonical allergen. It does reject, but through a different path than the one
   the sentence named (see below), so even a pass would not have evidenced inference.
3. **No seeded record can exercise the claim.** Of the sixty, exactly two carry a tag they do not
   declare, and both are `gluten` implied by a declared `wheat` - the implication table, not
   ingredient inference. The path the sentence described had no data to run on.

The claim is now true because the test builds a catalog for it: two records, one whose
`allergenTags` is `[]` and whose ingredient list alone implies `shellfish`, one that implies
nothing. Two meals fit inside the three the endpoint returns, so the assertion is "was rejected"
and not "did not appear", and the allergy-free run is the control proving the meal was reachable.
`shellfish` removes it and leaves the other; nothing else changes.

### What the three matching paths actually do, pinned

`conflictingAllergens` has three independent paths, and the difference between them is the
difference between a protected user and an unprotected one:

- **Canonical tag** - `shellfish` against the effective tag set.
- **Literal ingredient name** - `coriander` matches the ingredient "Coriander Leaves".
- **The term's own inference** - `seafood` normalizes to nothing, yet its inference (`fish`,
  `shellfish`) overlaps the meal's tags, so it rejects. I expected this case to fail when I wrote
  the test for it; path 3 exists exactly for the everyday word a person types, and it is now pinned
  so a later simplification cannot quietly remove it.

**R-30, recorded not fixed.** A term the lexicon has never heard of is matched only literally:
`coriander` rejects the meal and `cilantro` - the same plant - does not. TSD 5.5 types `allergies`
as free strings, so narrowing the field is an amendment rather than a fix, and the containment is
that P14 must offer the canonical list rather than a text box. Both halves are now a test.

## The fallback explanation cannot outrun the score

Every clause is a `detail` string the scoring policy itself wrote, so the sentence cannot claim
anything the score did not. Reasons are taken in descending points, tie-broken on
`SCORE_REASON_KINDS.indexOf` rather than on array position - the two coincide today only because
`scoreMeal` happens to emit reasons in declaration order, and keying the comparator on the contract
means a change to that emission order cannot silently reorder a sentence.

When every policy scored zero it says `"This one fits your preferences."` - the only claim the data
supports. Inventing a reason there would make `explanationSource: 'fallback'` a euphemism.

### The explanation was dishonest by omission, and that is a defect this phase introduced

The first implementation cited only reasons with `points > 0`. `disliked-ingredient` never scores
above zero, so **a meal penalised -50 was explained entirely in its favour**: a score of 3 out of
100 read as two or three reasons to eat it, with the one thing the user had explicitly asked to
avoid the only fact left out.

The section above was true of what the sentence said and false of what it omitted, which is the
harder failure to notice - a green suite and an honest-looking docstring agreeing with each other.
The heaviest penalty is now cited too, as `"<positives>, though <penalty>."`, or as
`"<penalty>, but it fits your other preferences."` when nothing scored in the meal's favour. Four
tests cover it, including the two-penalty case.

## Contract details recorded

- **No 503 on this endpoint** (Plan C-04), verified with Ollama pointed at a dead port: still 200,
  every explanation `fallback`. A recommendation is useful without prose, and PRD FR-009 says the
  feature degrades rather than fails.
- **`mealPeriod` is required and the server derives no time.** TSD 5.4: deriving it here as well
  would compute one fact along two paths that can disagree across a minute boundary or a timezone
  read. The client computes it from 4.3 and sends the result.
- **`z.strictObject`, so an extra body field is a 400.** A request body is a contract the client is
  expected to know; a query string is not, which is why the two validate differently.
- **`scoreReasons` are returned** so a score can be checked rather than trusted.

## Known limitations carried forward

- **`_config` is unused** in `recommendationsRouter`. It is threaded now because P19 reads
  `AI_ENABLED`, `OLLAMA_*` and `GENERATION` from it, and adding the parameter later would touch every
  call site. Named with the underscore the lint rule recognises.
- **One test is conditional on the fixture.** The null-nutrient goal assertion runs only if an
  `unavailable` meal reaches the top three; with 53 of 60 records unavailable it does today, but the
  guard means it would pass vacuously if coverage rose. Flagged to the verifier rather than left
  silent.
