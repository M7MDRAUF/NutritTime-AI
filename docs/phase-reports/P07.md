## The number this phase must be judged on

**Nutrition derives for 7 of 60 records. The other 53 carry four `null`s and a recorded reason.**

That is the all-or-nothing rule of TSD 7.4 working exactly as written - no partial sums, no
substituted averages, no meal showing `0` where it means unknown - but it is a thin result and it
would be dishonest to file it as a success. Two causes, and only one of them is fixable by effort:

1. **The binding table reaches 127 of the catalog's 351 distinct ingredient names.** Each binding is
   a deliberate choice against the real archive; they cannot be generated. The naive token-overlap
   matcher this replaced proposed `Bacon` -> _Bacon, meatless_, `Chicken` -> _Fat, chicken_,
   `Whole Milk` -> _Cheese, ricotta_ and `Flour` -> _Potato flour_. That is the near-miss failure
   T-07-07 forbids, and it produces wrong nutrition that looks right.
2. **FNDDS has no row at all for rosemary, mint, saffron, cardamom, allspice, bay leaf, garam
   masala, fenugreek, shallots, toor dal, ghee, celeriac - or plain wheat flour.** It is a food-
   consumption survey table, not a culinary one. Under all-or-nothing, one bay leaf blanks an entire
   meal, and no amount of binding work changes that.

`catalog.test.ts` asserts the derived count is **exactly 7**, not "at least 3". A floor cannot tell 7
from 3 and would stay green while coverage regressed. The number moves only deliberately.

**A dedicated catalog-coverage pass is scheduled after P18** (plan section 7). Raising coverage means
authoring densities and countable gram weights that nothing downstream can check (R-03), so sparse
and refusing beats dense and wrong.

## What the hand review found (T-07-04)

`docs/catalog-allergen-review.md` records the review of **all sixty records** - including the
fifty-three that needed no change, because an unrecorded "no change" is indistinguishable from an

The `fromage frais` miss was a gap in the shared lexicon, not just this record: `fromage`, `paneer`,

is a wheat blend; keeping it only hides a safe meal. The tolerable error runs one way.

## Defects found and fixed in this phase

1. **A catastrophic measure misread I introduced myself.** The sized-container pattern I added for
   `3 400g cans` also matched `400g` as 4 x 00 and converted it to **zero grams** - silently, on the
   commonest measure in the catalog. The separator is now required, and a test pins `400g -> 400`
   beside `3 400g cans -> 1200`.
2. **Two tests encoded premises the real data contradicts.** `tblsp` was treated as a typo to refuse;
   it is how TheMealDB spells a tablespoon (`"2 tblsp"`, `"3 tblsp chopped"` are both live). And
   `1 cup chopped` was refused as an unverifiable unit; the preparation word qualifies the food, not
   the amount, so refusing discarded real measures across most of the catalog for no accuracy gain.
   Both corrected with the reasoning recorded.
3. **A single-word preparation unit was not stripped.** `1 chopped` and `2 sliced` left `chopped`
   standing as an unrecognised unit, failing measures that plainly say "one onion".
4. **`no-console` had to be exempted for the seed script**, which is a hand-run CLI whose entire user
   interface is its output. The rule is **restated minus `log`** rather than switched off, because
   P01 learned that an `'off'` exemption silently drops the whole rule.

## Divergences recorded, not resolved unilaterally

- **X-15 - `fdcId` cannot be `string`.** TSD 7.4 declares it non-null. Measured: **44 of the
  archive's 1,882 ingredients publish no FDC ID on any macro**, including olive oil, unsalted butter
  and the canola, corn, peanut and soybean oils. Implemented as `string | null`; `usdaCode` keeps the
  row traceable and `sourceLabel` keeps its provenance. TSD 7.4 should be amended to match the data.
- **X-16 - the catalog package graph.** TSD 2.3 says `catalog -> (nothing)`; TSD 7.4 step 1 mandates
  using 4.1's text primitives, which live in the domain. Resolved toward 7.4, the more specific
  instruction. **The edge is build-time only**: `src/index.ts` imports nothing from `src/seed/`, so
  nothing reaching a device or a request path carries it.
- **The nutritionally-inert rule.** An ingredient whose four per-100 g macros are all exactly zero
  (salt, water) survives an unparseable measure. This is a consequence of all-or-nothing, not an
  exception to it: any mass times zero is zero, so the totals are provably independent of the
  quantity the measure failed to state, and reporting them is exact rather than estimated. The test
  is on the DATA, so it can never be claimed for a food that contributes something - a single
  non-zero macro fails. "Salt - to taste" appears throughout the catalog.

## What the independent verification changed

The gate was green and the phase was committed when verification reported. It found **two
CRITICALs**, and the first is the more instructive because it was **a defect my own fix
introduced**.

### CRITICAL - a hyphenated mass range was multiplied instead of refused

The sized-container repair (`3 400g cans` -> 1200 g) runs inside `normalizeMeasure`, which is
**before** the range guard. Its separator alternation accepted a hyphen - and a hyphen is exactly
what a range uses. The guard never saw the string:

```text
"4-5 pound"  ->  9071.85 g     (read as 4 x 5 = 20 pound)
"2-3 kg"     ->  6000 g
"3-4 g"      ->  12 g
"2-3 tbsp"   ->  correctly refused
```

Only the mass class was affected, which is why every existing range test missed it: all four used a
volume unit. `4-5 pound` is live in the catalog (`beef-brisket-pot-roast`), and it reached no shipped
number only because `Beef Brisket` happened to have no binding - an accident, not a control.

**This is the same `400g -> 4 x 00 = 0` class the phase had already fixed once, re-entering through
the fix itself.** The separator is now whitespace-only, so a hyphenated range falls through to the
guard and is refused, and six mass-unit range vectors pin it.

### CRITICAL - a duplicate binding key silently chose the wrong food

`BINDING_ENTRIES` declared `'basil'` twice: once as `2044 Basil, fresh` (23 kcal/100 g) and once as
`2003 Spices, basil, dried` (233 kcal). `new Map` takes the last, so **the dried spice won - a 10x
error, with the correct row already written down two hundred lines above it**. Worse, the surviving
entry carried _fresh_-basil gram weights on a _dried_-spice row, so a `Bunch` derived 58 kcal against
a true ~5. Removed, and a test now asserts `BINDING_ENTRIES.length === INGREDIENT_BINDINGS.size`,
because nothing detected this class at all.

### Other defects fixed

1. **The documented "all-preparation unit becomes a bare count" behaviour did not exist.** The
   consumer filtered the empty stripped unit out of its candidates, so `1 chopped` fell back to
   `chopped` and failed. **It blocked 15 of the unavailable records - the single largest cause.**
2. **`leaves` folded to `leave`, not `leaf`,** so a binding declaring `leaf: 0.5` was never consulted
   and `6 leaves` failed with the weight sitting in the table.
3. **Four alias keys contained hyphens and could never match**, because `normalizeText` collapses
   punctuation to spaces. `fish-pie` reported _"Semi-skimmed Milk matches no ingredient alias"_ while
   the table contained exactly that entry. `parmigiano-reggiano` was dead twice over - unreachable
   key _and_ a target that was itself an alias, which the resolver does not chain.
4. **Nine bindings named a materially different food** where the archive carries the right row.
   Corrected: canned chickpeas split from dry seed (a can weight on the 378 kcal dry row made
   `1 can` derive 1512 kcal against ~352); condensed milk (321, not whole milk's 61); marshmallows
   (318 and a 0.21 density, not sugar at 401 and four times the mass); cocoa powder (228, not dark
   chocolate's 550); **fresh ginger root (80, not the dried spice's 335)** - the catalog measures it
   as `1 inch` and `2 tsp shredded`, plainly the rhizome; chicken thigh (221, not breast's 120, with
   fat out by 6x); cherry tomatoes (15 g each, not a full tomato's 123 - an 8x error on a count).
   **`clotted cream` and `fromage frais` are now deliberately UNBOUND**: the archive carries neither,
   and clotted cream is 586 kcal against heavy cream's 340 on the dominant ingredient of a meal. An
   unavailable meal beats a wrong number.
5. **R-16's control was missing.** The plan names it explicitly - "P07 must validate declared tags
   against the taxonomy at seed time and fail the write on an unrecognised one". `allergenAdditions`
   is `readonly string[]`, so a typo like `treenut` would pass the schema, pass the superRefine, pass
   every test, and resolve to nothing at runtime. `seed.ts` now fails the run on a non-canonical tag.
6. **A shredded-cheese density moved a committed figure.** `0.4 g/ml` against USDA's own 1 cup
   shredded = 113 g (0.478). `chicken-enchilada-casserole` is 59% cheese by energy and moved from
   **323 to 357 kcal/serving**. This is R-03 exactly: nothing downstream could have detected it.
7. **`white rice` and `rice` bound the same USDA code at two different densities** (0.85 and 0.78).
   A table that disagrees with itself. 0.78 is correct - USDA gives 1 cup raw long-grain as 185 g.
8. **A dual-unit measure kept the first half, not the metric half.** `6oz/180g` is live and derived
   170.10 g against the stated 180.
9. **Three test names claimed more than their bodies checked.** `describe('three meals verified by
hand')` worked exactly one of them, and that one used 0.85 g/ml for sugar where the binding says
   0.845 - so the "independent hand check" was checking a different computation from the one the code
   performs. Both rounded to the same integer, which is why it survived. All three are now worked in
   full, per ingredient, with the arithmetic in the test. And `it('names the ingredient that blocked
every unavailable record')` asserted only `reason.length > 10`; it now checks the reason actually
   quotes one of that meal's own ingredient names.
10. **A comment in `derive.ts` attributed a behaviour to a schema rule that does not exist.** The
    superRefine does not require `dataset` and `servings` to be absent on an unavailable record; that
    is a deliberate choice, and it now says so.

### Verification that held

The verifier recomputed **all four macros of every derived meal by hand** from the per-100 g table
and the raw measures, without running `derive.ts`: **all twenty figures reproduced**. It verified all
106 committed nutrient rows line-by-line against the real archive - **0 discrepancies**. It confirmed
the all-or-nothing rule holds on all 60, that no record reports `0` for unknown, that `seededCatalog`
is genuinely `unknown` and nothing outside `src/seed/` imports a seed module, and that the
one-directional union in the hand review never removed an inferred tag. It read all 60 ingredient
lists looking for a missed allergen and **found none**.

It also judged the nutritionally-inert refinement: the reasoning holds, the implementation matches it
exactly, and it enumerated **every all-zero ingredient in the archive - 19, all genuinely zero-macro**
(salt, waters, unsweetened teas, baking soda, and nine nutrient placeholders). So it cannot admit a
contributing food on this dataset. It remains an undocumented deviation from TSD 7.4's literal text
and should be ratified there.

## Known limitations carried forward

- **Nutrition coverage, 5 of 60.** The catalog-coverage pass after P18 owns it. Until then P16's
  "Not available" nutrition row is the common case, not an edge case, and must look deliberate.
- **`R-03` stands and is now the dominant risk in this package.** Every density and countable gram
  weight is an authored conventional figure. A wrong one scales one ingredient and nothing
  downstream can detect it.
- **`derive.ts` rounds but never clamps.** TSD 7.4 step 4 says "round to the nearest integer, and
  clamp to §3.3's ranges". In practice not clamping is SAFER - an out-of-range figure aborts the
  write at the validation step rather than being silently capped at 2000 kcal - and no committed
  value is out of range. Recorded as an unrecorded deviation made deliberate. **R-23.**
- **The parenthesised-metric preference only recognises abbreviated units.** `8 ounces (230 grams)`
  keeps the ounces and derives 226.80 g against the stated 230. Every instance is within ~2%, so
  nothing committed is materially wrong, but the feature is half-implemented. **R-24.**
- **`vegetable broth` and `chicken broth` declare `cube: 4`.** A stock cube is 4 g of concentrate,
  but the bound row is ready-to-serve broth at 5 kcal/100 g, so three cubes derive ~0.6 kcal instead
  of ~28. Trivial in magnitude, wrong in semantics. **R-25.**
- **`honey-teriyaki-salmon` contains no honey.** TheMealDB record 52773 lists five ingredients and
  the honey exists only in the instruction text. Nothing was dropped in mapping - all twenty slots
  were read - so the derived `4 g` of carbohydrate is the ingredient list, not the dish. It is one of
  only seven figures the product currently shows. Upstream data, not a defect here, but it is a
  reminder that a derived figure is exactly as complete as the recipe it came from.
- **About 25 of the unavailable records are blocked by an ingredient the archive plainly carries**
  and for which no binding was written - `Mackerel`, `Beef Brisket`, lamb, strawberries, peanut
  butter, ground almonds, rolled oats, prepared mustard, cocoa. The coverage pass owns them.
- **`meals.json` is regenerated, not hand-edited.** Editing it directly would pass boot validation
  and silently contradict the seed script. Re-run `npm run seed`.
