reset. `Plan.md` §5 calls this "destructive-action territory".

## What verification found

### CRITICAL — a write in flight resurrected the user's data after a confirmed wipe

A store write already in flight when `clearAllStorage` ran landed **after** the keys were removed. So
the user confirmed "erase all data", the app returned to onboarding, and `preferences` came back
holding `{"diet":"vegetarian","allergies":["peanut"]}`. Nothing reported it, because the write
belonged to a store instance that had already been discarded.

The first fix — unmount the storage subtree before clearing, then read the keys back and re-clear any
that reappeared — was then **dismantled by V10**, correctly:

- `createStore`'s drain never checked `mounted.current` **before** `await repository.set`, so an
  unmounted store's queued write proceeded anyway;
- the three verification passes resolve in microtasks while a real AsyncStorage write takes
  milliseconds, so the read-back catches far less than it appears to;
- and the regression test released its held write from **inside pass one**, proving only the
  narrowest case.

V10's verdict — _"narrowed, not closed" understates it; by ordering, nearly the whole window
remains_ — was right. `createStore` now checks `mounted.current` before the write, which closes the
**queued** half outright and is covered by a new test in `createStore.dom.test.tsx`. The in-flight
half is **R-53**, and the honest account is that a write is in flight on _every_ cold launch because
`createStore` projects on mount (**R-54**) — so this is not "you would have to be quick".

**No timeout was added.** No document gives a figure and inventing one is a §8 stop condition.
Closing it properly needs a cancellable driver write, and TSD §6.4 fixes the driver to four methods —
raised for the user.

### MAJOR — a partial reset showed the user the data they had just erased

**V10.** `ALL_SETS` cleared `onboarding` **second**, so any early stop dropped the app into setup
with the user's name, diet and allergies prefilled from the surviving keys. And because
`RootNavigator` does not mount Settings in the onboarding phase, **`resetError`'s only render site did
not exist exactly when it fires** — the test asserting its visibility mounted `SettingsScreen` with no
navigator, so it passed against a tree the app never builds.

Reordering alone would not have fixed it, as W7 established: nothing stops early, so `onboarding`
would still have gone alongside a surviving `preferences`. The keys are now two groups — the data
sets, then onboarding, **and only if the data pass fully cleared** (**S-52**). The two claims were
probed **separately**, "since one edit failing both would have proved neither": ordering-only fails
`expected 1 to be 7`, gate-only fails `expected 'onboarding' to be 'app'`.

### MAJOR — a confirmed clear whose write failed said nothing

**V3 and V10**, independently. The screen read `preferencesStore.useStatus()` for `entryStatus` only
— never `saveError`, `saveBlocked` or `retrySave`, and never read the favourites or custom-meals
status at all, while three other screens did. So: "This removes 2 favourited meals from this device",
the list empties, and every favourite is back at the next launch. V3's green-staying mutation is
precise — suppress `repository.set` for the favorites key alone.

The three clear-on-confirm tests had asserted store memory through the probe and never read the
driver, **though the same file already read the disk for the AI toggle** — the technique was in hand
and simply not applied to the assertions that needed it. All three now decode the driver and assert
the untouched sets are still present.

### MAJOR — the theme switch changed no pixel, and no screen test could have caught it

**V3 and V13.** `App.tsx` hard-coded `ThemeProvider mode="system"`, so T-18-04's control dispatched
correctly, stored correctly, and moved nothing. **The screen was right and the wiring above it was
missing** — the same shape as P14's boot-phase defect, which only the first end-to-end run found.

Fixed with nested providers (**S-54**): an outer `ThemeProvider` at `system` themes the splash, which
renders _during_ hydration and calls `useTheme()`, and an inner one inside the preferences store
governs everything below. The ordering is forced, not chosen. `StatusBar style="auto"` was then found
sitting above the inner provider, resolving from the **device** scheme — so dark theme on a light
device gave dark glyphs on a dark canvas. There is now exactly one, inside the provider: child
effects run before parents', so an outer instance kept "for the hydrating window" would run last and
quietly restore the bug.

### MAJOR — the disclaimer flag had no writer at all

**Four auditors found this independently** — V3, V6, V9 and V12. `uiActions.acknowledgeDisclaimer()`
existed with a schema, a default and a Settings surface, and **nothing in the app ever dispatched
it**. So `disclaimerAcknowledged` could only ever be `false`, and Settings told every user they had
not seen the allergen notice — false for anyone who had opened Home, where FR-007's disclaimer always
renders. Half of T-18-01's acceptance was unmeetable.

V12's observation is the one worth keeping: _"The sibling gap was caught and closed (`changeTab` →
`TabNavigator.tsx`); this one was not."_ The orchestrator wired the `lastTab` writer during
integration and missed the disclaimer writer — the identical class of gap, two fields apart in the
same store.

Dispatched from `HomeScreenWithFocus` now (**S-56**), since S-46 makes the disclaimer a persistent,
non-dismissible surface — so "acknowledged" can only mean "has been shown it".

## The convergence, and why it was the most useful triage signal

Four auditors found the missing dispatch. Two found `resetError`'s unreachable render site. Two found
the silent clear failure. Two found the preferences-`recovered` gap. Two independently corrected
`failOn('getItem')` to `failOn('multiGet')`.

**A finding one auditor reaches is worth checking twice; one that four reach independently is real.**
With 28 findings to triage, that was the cheapest available ranking.

## The end-to-end run found what no unit test could — including in a parked test

W14 converted P14's parked FR-003 `test.fixme` into a live passing test, and found that **it would
have been red, not green, if simply un-parked**: it tapped _peanut_, and none of the three default
meals carries peanut. The allergen is now derived from the meals actually on screen, and FR-003's
_discard_ is observed by gating the re-request rather than inferred. That is P15's peanut lesson
recurring one layer up.

It also measured that **T-18-06's "all six keys cleared" cannot be asserted literally**: five keys
are re-created within the same frame holding their fallbacks (R-54). The spec asserts something
stronger instead — no fragment of the seeded state anywhere in `localStorage`, every key equal to its
documented default, and `meta.firstLaunchAt === lastLaunchAt` as positive proof the key was _removed_
rather than overwritten.

## Known limitations carried forward

- **R-53 — the reset race is narrowed, not closed**, and ships as an `it.fails`.
- **R-54 — every store rewrites its key at every launch.** Four costs, ranked in the register; the
  worst is that a bound-truncated read is committed to disk before the user is told. The obvious fix
  is wrong — a plain "skip the first run" breaks `favorites`, whose `create` de-duplicates.
- **R-55 — a chip group conveys no selected state on web.** `ChipRow` renders a `radiogroup` of
  `button`s; `aria-selected` is invalid on `button` and `accessibilityState` is unmapped by
  react-native-web 0.21.2, both verified in `node_modules`. It affects **four groups across two
  screens**, so it is an accessibility pass with its own gate. Settings works around it locally and
  says why at the site.
- **The "not yet seen" branch of the disclaimer row is now unreachable in the app phase**, since
  HomeTab mounts first and dispatches. Kept, and recorded rather than deleted — but noted so nobody
  "fixes" it by removing the dispatch.
- **A `radiogroup`-free theme row makes Settings stylistically different from Dietary Setup.**
  Deliberate, and stated at the row.
- **X-31 remains open and untouched.** Settings is now a second entrance to the meal-time form, so a
  night-shift profile is blocked from one more place. Still the user's decision.
