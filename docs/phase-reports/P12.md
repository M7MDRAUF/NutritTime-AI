The largest phase in the window: Expo scaffold, theme runtime, sixteen shared components, storage,
navigation and the API client. Four agents on disjoint surfaces, then integration, then an
independent verification that found nine MAJOR defects a green gate could not.

## Two dependency amendments, both decided by the user

Each began as a **stop condition** under this plan's §8 — "a task needs a dependency TSD §2.1 does
not pin" — and neither was taken unilaterally.

**A-11: `@expo/vector-icons@15.1.1` + `react-native-svg@15.15.4`.** TSD §6.7 specifies an `Icon`
component and §2.1 pinned no icon library, so T-12-04 built a 17-character Unicode glyph map. It was
a correct answer to the constraint and a bad answer to the problem: **a glyph renders only if the
resolved face has it, and a face that lacks one draws a tofu box rather than falling back.** `search`
was U+2315, quite possibly absent from Inter and needed by `SearchField`; there is no house, compass,
chat, bookmark or gear character with dependable coverage at all, so the five tabs shipped with
`tabBarIcon: () => null`. **The agent that built it said so plainly instead of papering over it**,
which is the only reason this became a decision rather than a defect found on a device.

`Icon` was reimplemented behind the **same `IconName` / `ICON_NAMES` API**, so not one consumer
changed a line — which is what S-12 (derive the type from the map, never hand-list it) bought.
Material Community Icons rather than Feather for one reason that matters: **Feather has no filled
heart**, and a favourite needs filled and outline to be two different marks because PRD §10.5 forbids
colour as the only carrier of a state.

**A-10: `@expo-google-fonts/inter@0.4.2`.** X-07 fixes the typeface as Inter and the app did not have
Inter. `expo-font` was a declared dependency with **no importer anywhere**, there were no font assets,
and `typeFamily.sans` was the CSS stack `'Inter, -apple-system, Roboto, sans-serif'` — which React
Native's native `fontFamily` does not parse as a fallback list, because it takes one family name. Two
independent failures, and it rendered correctly on web, where the stack really is CSS. That is
exactly how it survived P11 and P12 unnoticed (R-32).

A second native constraint set the shape of the repair: **React Native does not synthesise weights
for a custom family**, so `fontFamily: 'Inter'` with `fontWeight: '700'` gives regular Inter on
Android. `typeFamily` became a weight → face map, and `App.tsx` loads exactly the four faces the
scale names. **A font failure cannot brick the app**: the boot gate advances on
`fontsLoaded || fontError !== null`, degrading to the platform face rather than holding a splash
screen forever.

## What verification found, and what changed

The gate was green — 58 files, 1417 tests — before the verifier started. It found **nine MAJOR
defects and fifteen minor ones**. The two that matter most were both invisible for the same reason.

### A WCAG failure that shipped because the pairing had no row

`component.ts`'s four `toast.tone*` tokens were `status.*`, which is authored against
`surface.canvas`. `toast.background` is `surface.inverse` — its **opposite in both schemes** — so
every one of the eight pairings measured **1.49:1 to 2.76:1**, under WCAG 1.4.11's 3:1 for a non-text
indicator and under the AA-in-both-themes PRD §10.5 requires.

`contrast.test.ts` verified every text tone on canvas, raised, sunken and overlay. `surface.inverse`
is none of those, and **no semantic token names it**, so no row could exist. **A missing row looks
exactly like a passing one.**

The repair authored no new colour: an inverse surface has the brightness of the _other_ scheme's
canvas, so `statusOnInverse` is simply the other scheme's `status`, used against the surface
brightness those values were authored for. Every pairing now clears **5.78:1 to 10.69:1** — AA for
text, not merely 3:1 for an indicator.

The same argument then found a second failure the verifier caught: the exemption row for
`border.subtle` measured against `surface.canvas` **alone**. Dark `border.subtle` was `ink[700]` and
`surface.overlay` is `ink[800]` — adjacent steps of one ramp — so the `Divider` separating a dark
`Sheet`'s header from its content measured **1.0469:1**, below this file's own `VISIBLE_MINIMUM` of
1.05, while the test reported 1.3662 and passed. No ramp step fits (the next one up is 3.19, past
1.4.11 and already `border.default`'s value), so `#2B423B` was authored: 1.301 at worst across all
four dark surfaces.

`contrast.test.ts` gained rows for `surface.inverse`, for all four surfaces on every exemption, for
`effect.skeleton` (which had **no assertion anywhere**), and a reverse assertion that the canvas
tones still fail on the inverse surface — so the two families cannot quietly converge without someone
being told. A new `component-contrast.test.ts` covers the composed tokens, because the defect lived
in `component.ts` and a semantic-only suite structurally cannot see it.

### A guarantee stated in bold that was false, and a test that could not reach it

`hydrate.ts` says **"Never rejects, under any driver behaviour"**. It rejected. The quarantine
removals were built with a synchronous `.map((key) => driver.removeItem(key))`, and a driver whose
`removeItem` throws synchronously threw inside the callback — so `Promise.allSettled` was never
constructed, and `hydrateStorage` rejected, bricking the launch.

The test asserting the guarantee set `failOn` for `setItem` **and** `removeItem`. `setItem` failed
first, `writeQuarantineRecords` returned `false`, and the removal branch was skipped entirely: the
`removeItem` line was decoration, and deleting it changed nothing while the name claimed to cover
"every write and removal too". Three tests replace it, splitting the two failures and asserting in
both directions — the corrupt bytes survive when the removal fails, and the key is actually gone when
it succeeds. Reverting the fix makes the new test fail with `driver refused removeItem`; probed.

### The rest

- **`boundary.test.ts` could not see a single `.tsx` file.** `'AppText.tsx'.endsWith('.ts')` is
  false, so the walker scanned 31 files and skipped **42** — every shared component, every navigator,
  the registry, and `ThemeProvider` itself. The file's docblock calls itself "the stronger of the two
  halves" because it reads the tree from disk; it was blind to every file its own argument names. The
  lint half did cover them, so the boundary was enforced — just not by this.
- **`PlaceholderScreen` rendered the only text outside the type scale.** Two bare `Text` elements
  with a colour and nothing from `theme.typography`, and no `allowFontScaling={false}` against an
  invariant `ThemeProvider` states in bold. Not the 4× bug — an element that never receives the
  pre-multiplied token has nothing to double — but it mattered more than it looks: nothing is
  registered yet, so **this screen is the visible app**, on every route. Now `AppText`.
- **Two divergent copies of `@types/react`.** `apps/mobile/package.json` pinned 19.2.7 while the root
  pins 19.2.18, so `npm run typecheck` compiled the same `.tsx` files twice against two different
  React type definitions. Both passing was luck. Removed.
- **`apps/mobile/tsconfig.json` contradicted TSD §2.2 in three ways**, only one of them recorded —
  and recorded in `Plan.md`, which is the lowest of the four ranks and cannot overrule a TSD section
  that specifies the file's contents. The documented `extends` array and the `@/*` alias are
  restored; `types: ["node","react"]` stays as a recorded addition, because without it TypeScript's
  automatic inclusion does not reach the root's `@types/node` from this directory and the four tests
  that read source files off disk do not compile.
- **The SQG-09 exception table had rotted in three ways at once.** Every `packages/design-system/...`
  path was dead after X-17's re-homing, so T-28-05 would have matched none of them. Three counts were
  stale by up to 82 lines. Three files exceeded the cap with no row, two since P08. And
  `contrast.test.ts` had reached **696 lines against the 459 its exception was granted at** — 42% past
  a cap it was already exempt from, which is how an exception becomes a blanket. Split rather than
  re-approved.
- **FR-001's traceability row cited `hydration.integration.test.ts`, which does not exist.**
  Corrected — and the row now also records that the guarantee is currently satisfied _vacuously_:
  `App.tsx` derives the boot phase from `useFonts`, `hydrateStorage` has no production caller, so
  "protected navigation cannot render before hydration" holds because nothing hydrates. T-14-06 is
  where it becomes real.

### Tests deleted for being decoration

Following the standard set in the P09/P10 re-audit — _for each assertion, what change to the code
would make this fail?_

- `Icon`'s "draws a glyph for every name it publishes" asserted that a string literal in a map is
  non-empty. Replaced with one that pins `ICON_NAMES` against the map it is derived from.
- A `Toast` `it.each` over four tones that recomputed the same four-glyph set every iteration, never
  read its parameter, and closed with `expect(tone).toBeDefined()` — the value `it.each` had just
  supplied. **Mine, written in this phase.** The test immediately below it makes the same assertion
  once.
- `linking.dom.test.ts`'s `params: {}` — `toMatchObject` treats `{}` as a subset of any object, so it
  passed whether or not the query param arrived. It arrives; now asserted.
- `AppText`'s `expect(fontFamily).not.toBe('')` now pins `'Inter_400Regular'`, which is the one
  component assertion that would catch an R-32-class regression.

And two comments were corrected rather than left to mislead: `allowFontScaling` is **unobservable**
in every dom test, because react-native-web does not forward it. Two files claimed it was pinned.
What is pinned is the arithmetic — 16 px at 1× must be 32 px at 2× — and the prop itself is
device-only (R-35).

## Three mistakes of mine, stated plainly

1. **I reported a contrast defect that was not one.** I asserted `card.imageText` against bare
   `card.skeleton` and read 1.10:1. The text is never on the bare skeleton — it sits over
   `card.imageScrim`. The test now composites the scrim over a pure-white photograph, the real worst
   case, which makes "the alpha was computed against white" checkable rather than a comment: 6.34:1.
   A false positive in a contrast suite costs exactly as much trust as a false negative.
2. **The compositor's own self-check caught me writing `#808080` where the answer is `#7f7f7f`.**
   `0x80` is 128/255, not 0.5. A contrast suite whose compositor is a percent out is worse than no
   suite, because every ratio it reports would be plausible and slightly wrong.
3. **I wrote "5.78:1 to 11.71:1" for the repaired toast pairings and 11.71 is not one of them.** It
   came from a `content.link` probe run while choosing the approach. The true range across all eight
   is 5.78 to 10.69. Corrected in `semantic.ts`.

## Judgements recorded rather than quietly decided

`design-system/DECISIONS.md` §7.1 and §7.2 carry **S-12 … S-35**. The ones that would be easiest to
get wrong silently:

- **S-20 — `DEFAULT_PREFERENCES` (A-09) assumes no restriction.** No allergies, `diet: regular`,
  `budget: medium`, and **`name` absent rather than empty**. An assumed allergy hides edible food and
  teaches distrust of the filter, which is the one thing this product cannot afford; a default name
  would be a name stored without ever being told one.
- **S-23 — "Working offline", never "You're offline".** PRD §10.2 says core features need no network
  and the server runs on the same machine, so it can be down while the phone's connection is
  perfect. The second wording is a claim the component cannot check and is usually false.
- **S-24 — `Toast` has no default `durationMs`, and an absent one means it does not expire.** WCAG
  2.2.1 treats "no time limit" as the conforming baseline and auto-dismiss as the exception needing
  justification. Inventing a dwell time would be inventing the exception.
- **S-34 — `MealCard.unavailable` is content, not control state.** No `aria-disabled`, and the card
  stays pressable: an unavailable meal's ingredients, allergen notices and nutrition are unchanged,
  so it is still worth opening. Calling a working control disabled would be the lie.

**X-14 is resolved** by authoring `customMealSchema`, which lifts three fields off and **delegates
the rest to `mealSchema`** so the `superRefine` invariants — all-or-nothing nutrition,
`source: 'user'` ⇒ `nutritionProvenance.origin: 'user'` — apply unchanged. Restating them would be
the duplication §12.3 calls a gate failure. **No TSD edit was made**; the prose is loosely worded
rather than wrong, and saying so is the user's call.

## Known limitations carried forward

- **R-35 / R-43 — jsdom has no font engine and no layout engine.** Touch targets, `allowFontScaling`,
  the onboarding gesture lock and whether a glyph is actually drawn are all **device-only** and close
  at P23. Contained by building to the minimum rather than computing it, and by asserting every icon
  name against the vendor's **shipped glyph map** — probed with a typo, which fails naming it.
- **R-36 — whole-key quarantine can cost real user data.** One malformed `CustomMeal` quarantines the
  whole key, and the ledger that holds the bytes is never surfaced, so there is no path by which a
  user recovers them. Implemented exactly as TSD §6.4 specifies, which is why it is recorded rather
  than changed.
- **R-39 — `IconButton` is unusable on an inverse surface** (2.32:1 light, 1.36:1 dark) and exposes
  no colour. `Toast` builds its controls from `Pressable` + `Icon` instead.
- **X-21 … X-26** are six document conflicts, all open and none resolvable in code: TSD §6.7
  contradicting itself on `Toast.stillAvailable`; Plan §14.1's "required" against TSD's optional;
  Plan §14.2 adopting `aria-describedby`, which React Native 0.86 does not declare at all;
  `NutritionBadge` having no macro discriminator, so three tokens have no consumer; RN having no
  `dialog` role; and PRD §10.4's "under 350" against SQG-09's "≤ 350", on which one file sits exactly.
- **Seven proposed token amendments** in DECISIONS.md §8.1, each a token a finished component reached
  for and worked around honestly rather than borrowing something adjacent.
