## What verification found

### MAJOR — a quarantined preferences key silently disabled the allergen notice

Found independently by **V1** and **V6**. The screen surfaced `entryStatus === 'recovered'` for the
**favourites** entry and not for **preferences**. A quarantined preferences record resets `allergies`
to `[]`, so `conflictingAllergens(meal, [])` returns nothing and the conflict notice never renders.
`HomeScreen` and `DietarySetupScreen` both check it; Home's own comment is the argument for doing it
here.

**The existing test rendered exactly that state and asserted the notice was absent** — correctly,
because the screen could not distinguish "no allergies declared" from "allergy list erased". A
passing test documenting a defect is the most expensive kind.

Both states are surfaced now, with **different copy and a deliberate asymmetry**: `recovered` says
the list was reset and to set it again; `unavailable` says nothing saved has been overwritten and
does **not** invite the user to re-declare, because on an unreadable key that would overwrite a
profile that is still intact. The warning is gated on the list actually being empty, so a clean read
with no allergies shows nothing and re-declaring in-session swaps the warning for a working notice.

### MAJOR — `recovered` meant two different things, and the copy told the wrong one

**V11.** `EntryStatus` carries one value for both "quarantined and emptied" and "truncated, 200
survived", and every surface rendered the quarantine wording. A user whose stored list was merely
shortened was told their data was gone **while their favourites rendered below the message**.

No document change was needed: a quarantine always returns the empty fallback, so `recovered` with a
non-empty list can only be truncation. The truncation copy now names which survive and says the
shorter list **has already been saved** — because `createStore` projects on mount (**R-54**), so by
the time the user reads it the overflow really is unrecoverable. Softening that would be a lie.

### MAJOR — FR-011's image attribution had no surface for any record in the catalog

**W6**, from its own catalog probe, confirmed twice: `provenance.imageSource` is null in **60 of 60**
records while all 60 display an image, every one hosted at `www.themealdb.com`, and `themealdbId` is
present in all 60. So the app showed sixty photographs and attributed none of them, against FR-011's
"source attribution for the recipe **and image**".

Fixed from facts the record carries rather than by inventing one — upstream's `strImageSource` is a
field for a _separate_ credit, and its absence means none is recorded, not that the image has no
source (**S-58**). A source comment stating the figure **backwards** ("null in 0 of 60") was caught
by V1 and corrected; the clarification beside it had been right all along.

### MAJOR — the `saveBlocked` surface became dead when the reducers were hardened

**V11 and V12.** Hardening the reducers to refuse at the bound meant `repository.set` can no longer
throw `bound-exceeded`, so `saveBlocked` is unreachable for all six keys. Dead UI reads as coverage.
**Merged rather than deleted** (**S-60**): TSD §6.3 publishes `saveBlocked` as "the case the UI must
present differently", so one reachable surface with two sources satisfies both. The honest note is
that its `saveBlocked` half is unprobeable because nothing reaches it — that is the finding, not a
testing gap.

## The probe that discharges R-31 for this screen

**R-31** records that no seeded record exercises allergen inference, so any claim about it must build
its own fixture. W8 proved why that matters: replacing the domain's `conflictingAllergens` with the
naive `meal.allergenTags.filter(...)` left **24 of 25 tests green**. The single test that caught it
was a fixture built for the purpose — the real `pad-see-ew` with its `allergenTags` stripped, so only
inference from "peanut oil" can match.

In its own words, and it belongs in the record rather than paraphrased:

> A future claim about inference on any screen must carry its own stripped-tag fixture and its own
> capability control; the number to remember is 24 of 25.

## Known limitations carried forward

- **R-56 — `IconButton` publishes no `accessibilityState`**, so the favourite toggle announces its
  action but carries no toggle _role_. TSD §6.7 fixes its props, so a seventeenth is an amendment;
  same class as P14's R-47/R-48. The interim conveys state three ways that work on every platform —
  the heart/heart-outline shape, an accessible name that changes with state, and a visible caption,
  all asserted in both directions. The exact edit is parked in the verification report.
- **An orchestrator instruction that was not implementable.** W1 was told to assert that toggling
  twice returns to the starting _reference_. A pure reducer receives only `(state, action)`; on the
  second call it has no access to the original object. W1 substituted the strongest true claims and
  added a **control set** asserting a real change must allocate — without which a reducer returning
  `state` from every branch passes every identity assertion in the file. That control set became a
  fleet-wide requirement, and V9 later found the one store that lacked it.
- **`expect(MAX_FAVORITES).toBe(STORAGE_BOUNDS.favorites)` cannot fail** while both are 200. Kept as
  a tripwire for a changed bound, with its limits recorded; the real coverage is the reducer's
  refusal asserted against `STORAGE_DEFINITIONS.favorites.bound`.
- **R-57 — `unavailable` is all-or-nothing in practice**, so the per-surface wording is defensive.
  Hydration is one `multiGet` and no store calls `repository.get()`.
- **X-32 — TSD §9 and `Plan.md` §18 both name `features/catalog/MealDetailsScreen`**; the code is at
  `features/details/`. Raised for the user rather than resolved.
