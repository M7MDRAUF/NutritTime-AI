## The rule this phase is really about

**The route ranks nothing and decides no diet question by its own rules.** Relevance comes from
`queryMeals` and diet compatibility from `isDietCompatible`, and the test asserts the response order
is _exactly_ the order `queryMeals` produces - not merely that it looks sorted. TSD 4.7 gives
relevance one implementation and two callers so the catalog screen and the assistant can never
disagree about what matches a phrase; a route with its own comparator would pass its own tests while
breaking that.

Diet filtering goes through `isDietCompatible`, so **a vegan meal satisfies a `diet=vegetarian`
filter**. `dietTags.includes('vegetarian')` would drop it and contradict the module every other part
of the system reads - the same defect P06's verification found in the answer resolver.

## Decisions recorded

- **The allowlist is the contract.** An unknown query parameter is ignored rather than rejected
  (TSD 5.4), so the known keys are picked out of `req.query` before parsing instead of handing Zod a
  `strictObject` over it. A client sending a stale parameter keeps working.
- **A repeated parameter is a 400, not a silent choice.** Express parses `?page=1&page=2` into an
  array; coercing it would pick one without saying so.
- **Name order is computed over `normalizeText`, not `localeCompare`.** A locale-aware comparison
  depends on the machine's collation, and an endpoint whose page boundaries move between two machines
  cannot be pinned by a test. Tie-broken by id.
- **Decimal digits only** for the integer parameters, for the same reason the config loader insists
  on them: `Number()` reads `0b111` as 7, which is in range and is not what the caller typed.
- **An empty result is 200 with `meals: []`**, never a 404. A narrow filter that matches nothing is a
  successful answer.

## A defect this phase exposed in P08

`routeTemplate` was logging `/:mealId` - **the mount prefix was missing**, so the list and detail
endpoints were indistinguishable in the log. P08's verification had flagged `request.route.path` as
router-relative and a trap for this phase; the first fix read `request.baseUrl` at log time, which is
too late - **Express sets `baseUrl` while dispatching into a router and restores it before the
`finish` event fires.** A `mountedAt` middleware now captures the prefix on the way in.

One P08 test also changed meaning: `/api/v1/meals/chicken-curry` used to log `(unmatched)` because no
such route existed. It now matches, so the template is the parameterised one - which is the point of
logging a template. A second test was added for a path no route claims.

## Known limitations carried forward

- **R-18 is visible here.** A search for `"don't want nuts"` leaves `don` in the query, because
  `normalizeText` turns an apostrophe into a space and only the contraction TAIL is a stop word. The
  clean fix is apostrophe-aware tokenisation in TSD 4.1.
- **`GET /api/v1/meals` does not filter by allergy**, by design: it is the catalog browser, and the
  safety filter belongs to the recommendation and chat paths that make claims. PRD FR-007 scopes the
  hard rejection to recommendations.
