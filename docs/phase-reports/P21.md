## 1. The five steps, in TSD §5.4's order

1. Parse → 400. `goal` or `budget` in `preferences` is a 400 because `chatRequestSchema` is
   `z.strictObject`.
2. `retrieveChatMeals`. Empty `eligible` → **200**, `answered: false`, `source: 'local'`.
   **No model call.**
3. `resolveAnswer`. An `UnresolvedAnswer` → **200**, same shape. **No model call.**
4. `AI_ENABLED === false` → **503 `ai_disabled`**.
5. Phrase through the lane → 200 `source: 'gemma'`, or 503 `ai_unavailable` / `ai_busy`.

**The step order is behaviour, and a probe proves it.** Hoisting the `AI_ENABLED` check above step 2
reddens three named tests — _"still answers 200 for an empty eligible set / a question no resolver
matches / a capability question with AI_ENABLED=false"_ — with `expected 503 to be 200`. A user who
switches the model off in Settings still gets every answer the domain can give without one.

**Citations are resolved from `namedMeals` by id, never parsed from the answer text** (T-21-03).
Parsing prose for meal names reddens its test; a citation derived from prose is a hallucination with
a link on it.

A health claim **and** an allergen-free claim, shipped as **200, with a citation attached**, to a

## 5. R-22 and X-15, surfaced and not invented

**R-22 is a real document collision.** PRD §7.4 lists **Capability** ("What can you do?") among six
answerable shapes. TSD §4.9's `UnresolvedReason` has **no `capability` member**, and
`answer-lexicon.ts:171-186` already files "what can you do" under `GREETING_TERMS` beside "hello",
with the collision noted in a comment. So **one copy string must serve both**, and a route cannot
give them different words.

One `CHAT_COPY.greeting` serves both, pinned by a test asserting the **same** string for both paths.
No seventh `UnresolvedReason` was invented — that is a TSD §4.9 amendment and a `packages/domain`
edit, which is a stop condition. **Raised for the user.**

**X-15 confirmed as correct behaviour:** a threshold question ("how many are under $10?") reaches
`incomplete-intent`, answers 200 with the no-information copy, and calls no model. TSD §4.9 defines
no numeric criterion and the domain refuses rather than answering with the whole-set size. Nothing
widened.

## 6. TSD §5.8's AI log line, written for the first time in eleven phases

`aiLogLine` has existed since P08. Until this wave it had **one consumer: its own test.**
`AiOutcome`, `AiLogFields` and `AiLaneName` had none at all.

That is verbatim the shape P08's own audit recorded for the error handler — a constant and a pure
function each tested, with nothing connecting either to the code that calls them — and it survived
that repair only because there was no AI lane to call it yet.

**Measured, not read** (D6, 76 captured lines, 29 error bodies, planted tokens):

- **30 AI lines across both lanes have exactly one distinct key set.** Zero planted
  question/answer/allergy tokens in any of the 76.
- `routeTemplate` correct on **8** request shapes including ones carrying query strings.
- **9 `details` shapes, all path-plus-fixed-string.** The `goal`/`budget` rejection — the one place a
  user's preference name is the thing being rejected — yields `{"preferences":["unexpected field"]}`,
  so Zod's `Unrecognized key: "goal"` never escapes.
- **6 error bodies, no answer text**, and all 5 causes of `ai_unavailable` produce **one identical
  body**, so a client cannot probe which containment rule fired.
- No invisible characters, by full codepoint enumeration. One `15.5`, naming `Plan` correctly.

`ai_busy` writes **no line at all**, deliberately: the lane rejects before `fn` runs, so a
`durationMs` would time a call that never happened and `unreachable` would report a stopped model for
a busy one. The refusal is still visible as the request line's `status: 503` with
`errorCode: 'ai_busy'`.

## 7. The one property no router could prove

TSD §5.5 says "one AI call at a time, **process-wide**". `createAiLane()` is per-instance, so
dependency injection cannot express that — what it can express is that every consumer shares **one**
lane, and `index.ts` creates exactly one app.

**And the obvious test for it would have passed under the bug.** "Hold the lane with one request,
fire the other, assert it degraded" passes with a lane per router: the second request takes its own
lane, calls a hanging model, and degrades anyway — just slowly, after its own timeout. The observable
outcome is identical.

So the two assertions are ones a second lane changes:

| Assertion                                                  | Under a lane per router                     |
| ---------------------------------------------------------- | ------------------------------------------- |
| the provider is contacted **exactly once**                 | `expected 2 to be 1`                        |
| the second caller gets **`ai_busy`**, not `ai_unavailable` | `expected 'ai_unavailable' to be 'ai_busy'` |

Both 503 and both retryable — **only the code separates "someone else is using the model" from "the
model is broken"**. Probed by giving chat its own lane: both tests redden, and the
`['fallback','fallback','fallback']` assertion above them **still passes**, confirming the obvious
version would not have discriminated.

A test that two _chat_ requests contend would pass with a lane per router, which is why one of the
two requests is always a recommendation.
