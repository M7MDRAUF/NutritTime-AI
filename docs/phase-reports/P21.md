# P21 — Grounded assistant

**All nine rows Completed.** The feature PRD §7.3 calls the headline, and the one the containment
design exists for.

**Written in two halves.** The server landed in commit `4e47b4d` alongside P20's, because the two
are genuinely interdependent — `chat.ts` consumes `ai/outcome.ts`, and `app.ts` wires **one** lane
and **one** provider to both routes. Splitting them would have required an intermediate commit where
`app.ts` mounts a router that does not yet exist: a red gate mid-phase, which the standing
discipline forbids more firmly than it asks for one commit per phase. §§1–8 below were written at
that point and are unchanged; §§10–13 cover the mobile half.

**Gate at completion:** prettier clean · eslint exit 0 · typecheck clean across 7 projects ·
**111 files / 2774 passed / 1 expected fail / 2 skipped** · `build:web` exported ·
**e2e 70 passed** (was 66) · audit exit 0.

**`Assistant` was the last route in the app without a screen. Every route in `SCREEN_ROUTE_NAMES`
now has one, and `PlaceholderScreen` is unreachable through the app** — it stays only because
`registry.dom.test.tsx` renders it to prove an unregistered route degrades rather than throwing.

## 1. The five steps, in TSD §5.4's order

1. Parse → 400. `goal` or `budget` in `preferences` is a 400 because `chatRequestSchema` is
   `z.strictObject`.
2. `retrieveChatMeals`. Empty `eligible` → **200**, `answered: false`, `source: 'local'`.
   **No model call.**
3. `resolveAnswer`. An `UnresolvedAnswer` → **200**, same shape. **No model call.**
4. `AI_ENABLED === false` → **503 `ai_disabled`**.
5. Phrase through the lane → 200 `source: 'gemma'`, or 503 `ai_unavailable` / `ai_busy`.

**The step order is behaviour, and a probe proves it.** Hoisting the `AI_ENABLED` check above step 2
reddens three named tests — _"still answers 200 for an empty eligible set / a question no resolver
matches / a capability question with AI_ENABLED=false"_ — with `expected 503 to be 200`. A user who
switches the model off in Settings still gets every answer the domain can give without one.

**Citations are resolved from `namedMeals` by id, never parsed from the answer text** (T-21-03).
Parsing prose for meal names reddens its test; a citation derived from prose is a hallucination with
a link on it.

**Reproduced independently three times** this window — from a unit harness, from an integration

Every previous statement about containment in this project has been a description. With the discard
bypassed, the integration suite measured the response body:

A health claim **and** an allergen-free claim, shipped as **200, with a citation attached**, to a

## 5. R-22 and X-15, surfaced and not invented

**R-22 is a real document collision.** PRD §7.4 lists **Capability** ("What can you do?") among six
answerable shapes. TSD §4.9's `UnresolvedReason` has **no `capability` member**, and
`answer-lexicon.ts:171-186` already files "what can you do" under `GREETING_TERMS` beside "hello",
with the collision noted in a comment. So **one copy string must serve both**, and a route cannot
give them different words.

One `CHAT_COPY.greeting` serves both, pinned by a test asserting the **same** string for both paths.
No seventh `UnresolvedReason` was invented — that is a TSD §4.9 amendment and a `packages/domain`
edit, which is a stop condition. **Raised for the user.**

**X-15 confirmed as correct behaviour:** a threshold question ("how many are under $10?") reaches
`incomplete-intent`, answers 200 with the no-information copy, and calls no model. TSD §4.9 defines
no numeric criterion and the domain refuses rather than answering with the whole-set size. Nothing
widened.

## 6. TSD §5.8's AI log line, written for the first time in eleven phases

`aiLogLine` has existed since P08. Until this wave it had **one consumer: its own test.**
`AiOutcome`, `AiLogFields` and `AiLaneName` had none at all.

That is verbatim the shape P08's own audit recorded for the error handler — a constant and a pure
function each tested, with nothing connecting either to the code that calls them — and it survived
that repair only because there was no AI lane to call it yet.

**Measured, not read** (D6, 76 captured lines, 29 error bodies, planted tokens):

- **30 AI lines across both lanes have exactly one distinct key set.** Zero planted
  question/answer/allergy tokens in any of the 76.
- `routeTemplate` correct on **8** request shapes including ones carrying query strings.
- **9 `details` shapes, all path-plus-fixed-string.** The `goal`/`budget` rejection — the one place a
  user's preference name is the thing being rejected — yields `{"preferences":["unexpected field"]}`,
  so Zod's `Unrecognized key: "goal"` never escapes.
- **6 error bodies, no answer text**, and all 5 causes of `ai_unavailable` produce **one identical
  body**, so a client cannot probe which containment rule fired.
- No invisible characters, by full codepoint enumeration. One `15.5`, naming `Plan` correctly.

`ai_busy` writes **no line at all**, deliberately: the lane rejects before `fn` runs, so a
`durationMs` would time a call that never happened and `unreachable` would report a stopped model for
a busy one. The refusal is still visible as the request line's `status: 503` with
`errorCode: 'ai_busy'`.

## 7. The one property no router could prove

TSD §5.5 says "one AI call at a time, **process-wide**". `createAiLane()` is per-instance, so
dependency injection cannot express that — what it can express is that every consumer shares **one**
lane, and `index.ts` creates exactly one app.

**And the obvious test for it would have passed under the bug.** "Hold the lane with one request,
fire the other, assert it degraded" passes with a lane per router: the second request takes its own
lane, calls a hanging model, and degrades anyway — just slowly, after its own timeout. The observable
outcome is identical.

So the two assertions are ones a second lane changes:

| Assertion                                                  | Under a lane per router                     |
| ---------------------------------------------------------- | ------------------------------------------- |
| the provider is contacted **exactly once**                 | `expected 2 to be 1`                        |
| the second caller gets **`ai_busy`**, not `ai_unavailable` | `expected 'ai_unavailable' to be 'ai_busy'` |

Both 503 and both retryable — **only the code separates "someone else is using the model" from "the
model is broken"**. Probed by giving chat its own lane: both tests redden, and the
`['fallback','fallback','fallback']` assertion above them **still passes**, confirming the obvious
version would not have discriminated.

A test that two _chat_ requests contend would pass with a lane per router, which is why one of the
two requests is always a recommendation.

## 9. The mobile half — eight files, none over the cap

`features/assistant/` holds `AssistantScreen.tsx`, `AssistantTurnRow.tsx`, `useAssistant.ts`,
`assistantCopy.ts`, three test files and a harness. **Every one is ≤350 lines**, split that way
deliberately so none needed a §17.1 row the author could not own. `useAssistant.ts` is at **345**,
and its own report says the next addition needs a split rather than an exception.

**No new shared component.** TSD §6.7's inventory stays at sixteen; the screen composes existing
ones.

### T-21-05 — the 500-character limit, enforced at two doors

`maxLength` on the field, **and** `validateQuestion` in front of the request — because
`AssistantParams.seedQuestion` means a **deep link can carry a 501-character question straight past
the input's `maxLength`.** Nobody briefed that second door; the author found it.
`ASSISTANT_MAX_QUESTION` is pinned to `chatRequestSchema` in both directions rather than restating
`500`.

**The transcript is `useState` and nothing else** — no store, no storage key, no `createStore` call.
PRD §7.3: "the on-screen transcript is a display concern only", and PRD §10.3 forbids a stored
question. Probing it by adding a persistence effect **reddened an existing test**, so the property
was already pinned and nothing had to be added.

### T-21-06 — citations that can be followed

Rendered from `ChatResponse.citations` alone, each navigating `MealDetails` with
`origin: 'assistant'` — the value `NAVIGATION_ORIGINS` has carried since P12 for exactly this
screen. Paired with a no-citation answer that renders no block, so the presence assertion is not
satisfiable by a component that always renders the container.

### T-21-07 — and the state that is not an error

**`answered: false` renders as an _answer_** — the server's own copy, an `info` tone — because it
arrives as HTTP 200 with `source: 'local'`. Rendering it as a failure would tell the user the app is
broken at the moment the app has answered them correctly.

Distinctness is asserted **in both directions and by glyph**, not just by text, and the three 503s
map **by code rather than by status**: `ai_disabled`, `ai_unavailable` and `ai_busy` are all 503 and
mean three different things.

## 10. A ruling the documents required, and the client gate it produced

**Settings promises what the wire could not deliver.** `RecommendationRequest` carries `aiEnabled`;
`ChatRequest` does not, and TSD §5.4's step 4 reads `config.AI_ENABLED` — the **operator's** switch.
So the user's own toggle governed Home and did nothing for the assistant.

**PRD §7.3:111 settles it:** "Report the assistant as unavailable — never substitute a generated
answer — **when AI is off** or Ollama cannot be reached." From the user's seat, their switch _is_
"AI off".

**Ruled: the client gates locally and makes no request.** No contract change, and that is
deliberate — TSD §5.4's own reasoning for the narrow chat preferences is that "a required field
that changes nothing is a field that will eventually be believed", so putting `aiEnabled` on the
wire would give the server two sources for one decision. The gate sits **first in `send`**, one
choke point, so `ask` and `retry` both inherit it, with a test named for the wrong placement:
_"refuses a retry while the user has AI switched off"_.

**And the gate made existing copy false.** The disabled state said the model was "switched off where
the server runs" — true when written, and with a client gate that state has two causes of which the
user's is now the common one. A true-when-written sentence had become a false specific claim. It now
names both and points at Settings, and `actionLabel` stays `null` because a retry cannot fix an
operator's switch.

## 11. T-21-09 — and the first end-to-end proof of R-21

Two specs, 4 passing across both viewport projects. `AI_FAKE=true` makes them evidence rather than
theatre: route, retrieval, resolution, prompt build and containment all execute and only the socket
is replaced, so **a superlative asked through the UI gets a real domain-resolved answer with real
citations.**

The citation set is asserted **equal to the domain's winner set by id**, catalog-derived, with the
winner's figure present in the answer and **the runner-up's name absent**. Then the citation is
**clicked**, landing on the detail screen with the actual `GET /meals/:id` observed — because a
citation you cannot follow is a decoration.

**And a measurement the spec author took turns this into R-21's first end-to-end evidence.**
For that question, `scope.context` is the catalog's first five — cheapest **$6.50** — while
`scope.eligible`'s cheapest is **$2.50**. So the superlative's winner is genuinely **outside** the
retrieved five. R-21 was designed into P19 on reasoning alone, three phases before anything could
exercise it: containment compares citations against `resolved.namedMeals`, and had it compared them
against `scope.context`, **this spec would fail**.

### "Does not hang" needed more than the text, and a probe proved it

Leaving `pending` set after the disabled branch left **the banner visible, inside the time bound,
with the `-pending` testID count at 0** — and _only_ the `role="progressbar"` assertion fired. A
spec that merely found the disabled copy would have passed with a spinner stuck on screen forever,
which is the failure a user cannot distinguish from a broken app.

So the assertion is the terminal state **within `TERMINAL_MS = 5_000` with the elapsed time
asserted**, plus `role="progressbar"` count 0, `aria-busy="false"`, and the button enabled.

### What the harness structurally cannot reach, stated rather than faked

Flow 6 has two disabled paths. The **user's switch** is driven through the real Settings toggle, with
a switch-back-on control on the same page. The **operator's switch** is unreachable: the harness sets
`AI_FAKE=true` and no `AI_ENABLED`, fixed before the first spec runs. Covered honestly elsewhere —
`chat.integration.test.ts:518` and `Assistant.dom.test.tsx:152`. **No 503 was faked to pretend
otherwise.**

## 12. A failure shape that arrived from finishing the work

Registering the last screen emptied `register.dom.test.tsx`'s `UNREGISTERED` list — and **an empty
record silently satisfies every `for` loop over it.** Two assertions there stopped making a claim at
the moment the final exemption was removed. Not carelessness: completing the work hollowed out the
test that had been tracking the incomplete part.

Now asserted explicitly — `expect(Object.keys(UNREGISTERED)).toStrictEqual([])`, plus the registered
set matched against the whole route table — so a future route added without a screen fails rather
than joining a list nobody iterates.

`explore.spec.ts` was updated the way that file's own comments prescribe. It had already been revised
twice — Home at P15, Saved at P17 — each time "to the stronger claim rather than deleted, because a
registry with a screen behind it is the stronger claim". It now asserts `assistant-screen`,
`assistant-idle` **and** `assistant-question`, because the root testID alone would be satisfied by a
component that mounted and rendered nothing usable.
