## 1. R-44 is closed, and the row describing it was wrong in three ways

The phase's headline defect — a query-param deep link landing on Home, a path restoring, a cold
`goto('/settings')` rewriting to `/home` — is fixed and asserted live at
`e2e/specs/explore.spec.ts:373`: _"applies a query param from the URL, which is R-44 verbatim"_
does `page.goto('/explore?query=chicken')` and asserts both the screen and
`toHaveURL('/explore?query=chicken')`. Re-measured independently in an out-of-tree replica **against
a live rival `ui.lastTab`** — the exact condition the original symptom was reported under — and
`/settings`, `/saved` and `/meal-form` each land on their own screen with no rewrite.

**And the recorded row was false three times over**, which is why it is quoted in the register now:

1. It named the marker a **`test.fixme`**. It was a `test.fail`. That matters: a `fixme` is
   _skipped_ and would **never** have turned red when the behaviour was fixed, while a `test.fail`
   does. The row promised a property the marker it named could not deliver.
2. Two of the recorded **symptoms** were false.
3. The cause was identified and was never `linking.prefixes`.

**The generalisation, now the fifth instance this project has recorded:** a risk row is a hypothesis
with a date on it, not a fact, and it must be re-measured before it is budgeted for.

## 2. T-22-04 — a library default that cost the browser's Back button

`backBehavior="history"` on `Tabs.Navigator`, chosen after measuring **all six** library behaviours
against the real `SwitchRouter` rather than reading their names:

| behaviour                                       | measured                                                                                           |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `firstRoute` / `initialRoute` (the **default**) | pushes **once ever** — entries 1→2→2→2→2, so **two Backs leave the site** after four tabs          |
| `order`                                         | walks the tab _bar_, not the visits: Home→Settings→Explore gives 2 entries and Back skips Settings |
| `fullHistory`                                   | keeps duplicates — a ping-pong is 4 entries where the user made 2                                  |
| `none`                                          | refuses immediately                                                                                |
| **`history`** (shipped)                         | 4 visits → 4 entries, Back walks `/saved→/assistant→/explore→/home`, the 5th exits                 |

Cost, stated rather than buried: on Android, hardware Back from a deep-linked tab exits the app. Web
is unaffected, because a cold load is one entry either way.

**Reverting the fix reddens 2 of 55 dom tests and both are new.** The pre-existing suite was blind
to it.

**And a docstring claimed the wrong cause.** `linking.ts`'s comment _and_ a test's name both said
`Tabs.initialRouteName` created the back target. It does not — histories are identical with and
without it, across all six behaviours. The **default** did. The test now pins the `initial: false`
effect that line really has.

## 3. T-22-06 — two recorded risks were wrong in the SAFE direction

Measured against a real `localStorage` through the shipped driver, unmocked, including a genuinely
quota-exhausted Chromium origin:

- **R-51's latch is impossible on the web export.** The web driver wraps `setItem` in a promise
  executor, so a quota refusal is a **rejection** and every write settles — raced against a 250 ms
  timer it resolves `rejected`. The row said "certain to matter at P22", which would have sent the
  next reader to harden the one surface that was already safe.
- **R-53's reset race is native-only.** `localStorage.setItem` is synchronous, so a write that has
  started has already landed before `clearAllStorage` reads back. The gap needs a driver whose write
  can be _pending_ across the clear.

Both rows corrected. R-60 gains a data point in its favour: on the web the retry offered for
`write-failed` genuinely succeeds once space is freed.

**A refusal subtlety worth keeping:** a full origin refuses only writes that **grow** it, so R-54's
per-launch reprojection survives a full device — and that made two drafts of the agent's own test
pass vacuously.

## 4. T-22-07 — the row had no assertion at all, and the obvious one passes under the defect

`scrollWidth`, `clientWidth` and `overflow` had **zero** occurrences across `e2e/specs/*.ts`. So the
row was unpinned, and a four-viewport matrix on its own proves nothing about horizontal scroll.

**The trap, measured rather than argued.** `body.scrollWidth > body.clientWidth` is **false while
the defect is present**: with one real button widened to 520 px in a 320 px viewport, the button sits
**216 px** outside and the document probe still reads **0**. An overflow here is not a scrollbar a
user can find — it is a control outside the viewport, unreachable and invisible, with nothing saying
so.

**And the reason both this file's config comment and the fleet contract gave was itself wrong.** Both
attributed the blindness to `apps/mobile/dist/index.html`'s `body { overflow: hidden }`. Overriding
that reset left the document probe at **0**, and overriding the screen root as well left it at 0
again: **react-native-web gives every `View` `overflow: hidden`**, so the export's reset is only the
outermost layer. The conclusion was right and the mechanism was not — which matters, because a
reader who "fixed" the template would expect the naive probe to start working, and it would not.

**The observable that does work:** for a screen's own box and every box beneath it, none is clipped
horizontally by a box the user cannot scroll — the tightest `overflow-x != visible` ancestor's right
edge, viewport included, exempting anything inside an overflowing `auto|scroll` ancestor. Result:
**10 of 10 registered screens plus the tab bar = 11 surfaces × 4 widths = 44 measurements, 0
clipped.**

Two honest caveats the author raised unprompted: the app **branches on width nowhere**, so the matrix
is four measurements of one tree; and one kept assertion's falsifiability lives in the toolchain
rather than in this repository, which the docstring states rather than hides.

## 5. R-72 — a defect no box assertion can see, found by reading the screenshots

**All five bottom-tab labels are painted clipped at 320, 375 and 414 px** — `scrollHeight 12` against
`clientHeight 10`, with `overflow-y: hidden` — and **whole at 768**.
`@react-navigation/bottom-tabs` 7.18.18 styles the stacked label `{ fontSize: 10 }` with **no
`lineHeight`** (`src/views/BottomTabItem.tsx:431-436`) while the beside-icon variant it swaps to at
768 px sets `lineHeight: 24`.

**Every box reports as fitting**, so no `getBoundingClientRect` assertion can see it — including the
one T-22-07 had just added for this class of defect, because the box and the clip are the same
element and the box does fit. It was found by a human reading the screenshots `Plan.md` §20 asks for
as that row's evidence. **That is the argument for the Plan having asked for screenshots**, and this
report records it as such rather than as a lucky catch.

**Two fixes were tried from `TabNavigator.tsx` and both were reverted, measured:**

- `tabBarLabelStyle: { lineHeight: 16 }` (the design system's own smallest token) made it **worse** —
  `scrollHeight` went 12 → **16** against an unchanged `clientHeight 10`.
- Adding `height: 16` alongside changed nothing, and why is the useful part: **this explanation was FALSE and it is why both
  attempts failed.** `Label` passes style to a **single** react-native-web `Text`, and attempt one's
  own `scrollHeight` moving **14 → 16** proves the prop arrived. The label is a **compressed flex
  item** (`flex: 0 1 auto`): the library's metrics leave `49 − 1 − 10 − 28 = 10` px for a label
  needing 14, and no line-box style beats a flex basis. **Closed at P28 by sizing the bar (49 → 55)
  and setting no label style at all** — 14/14 at 320, 375 and 414; 24/24 at 768, untouched; touch
  target _improves_ 48 → 54. `beside-icon`, this report's own suggested remedy, was measured and
  **rejected**: it unclips but leaves each label 6 px of the 35–53 it needs at 320 px, rendering
  Saved and Settings both as "S".

So the fix is not a style on that prop. It needs `tabBarLabel` rendered as this project's own
`AppText`, which carries accessible-name consequences an existing suite asserts, or a library
upgrade. Neither is a one-line edit and neither was guessed at inside another phase's round.

**Pinned as a CHECKED gap**, not a described one: `e2e/specs/text-clipping.spec.ts` measures
`scrollHeight > clientHeight` on text elements — a different observable from box geometry, because
the difference is ink that was never drawn rather than a scrollbar — under
`test.fail(width < 768)`. A **blanket** `test.fail` was tried first and correctly turned red at
768 px, so the marker asserts **both** halves: clipped below 768, whole at 768. A `test.skip` on
three projects would have dropped the 768 claim, which is the evidence identifying the library as the
cause. A separate control with a much larger clip proves the measurement fires, so an
expected-to-fail cannot pass for the wrong reason.

## 6. A test that had encoded the defect as its expectation

`settings-reset.spec.ts`'s cancel-path test failed in **all four** projects at the gate. Not
contention, and not a regression: it reloads while the user is on the **pushed** `DietarySetup`
screen and asserted the tab bar was visible — which held **only because a cold load used to rewrite
the URL to `/home`**. R-44's closure removed the rewrite, so the relaunch now correctly restores the
screen the user was on, and the assertion began failing.

Fixed to assert the restore, plus the peanut chip still checked **after a real relaunch** — the
stronger claim, and the one this test is ultimately about — then in through the front door for the
shared data assertion. **36 passed** across four projects.

**The shape is worth naming: a spec can encode a defect as its expectation, and then fixing the
defect looks like a regression.** It is the same failure as a docstring that argues for a hole
someone has since closed, one layer out.

  and the same caveat applies to Explore's 8.
