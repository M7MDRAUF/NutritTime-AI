# P13 - Tracer Slice: Explore, End to End - Completion Report

One screen from device to database, plus the Playwright harness. Single-threaded on purpose: when
the vertical breaks, the phase has to say which layer broke.

**It earned its shape immediately. Five defects, none of which 1450 passing tests and six green
typecheck projects could see — because the app had never been bundled and the two halves had never
been run together.**

## What the slice found

### 1. The app could not be bundled at all

`expo export` failed on the first relative import it met:

```
Unable to resolve "./App.js" from "apps/mobile/index.ts"
  * App.js(.web.ts|.ts|.web.tsx|.tsx|.web.mjs|.mjs|...)
```

Every relative import in this repository ends in `.js` — required by `verbatimModuleSyntax` and by
Node's ESM resolution — and the sources are `.ts` and `.tsx`. **tsc substitutes the extension and so
does Vitest. Metro appends its `sourceExts`**, so it looked for `App.js.ts` and `App.js.tsx` and
never tried the real `App.tsx`.

Recorded as **X-27 and resolved in favour of the document**: `metro.config.js` now carries a
`resolveRequest` that substitutes for relative specifiers only, and only when the literal file is
absent, so a real `.js` still wins and nothing in `node_modules` can be redirected. The alternative
was to abandon the convention inside `apps/mobile`, which would have split the repository's import
style at one directory boundary and given the mobile app a rule none of the other five projects
follow.

`apps/mobile/src/imports.test.ts` is the cheap half of the guard: it re-derives from the tree that
every relative specifier has a real file behind it, under the same substitution rule the bundler
uses. Breaking the entry import again fails it in **57 ms**, naming file and line, instead of three
minutes into a bundle — probed. It does not replace building the app, which is why the build is in
the gate.

### 2. `web.output: "static"` requires `expo-router`, and this app uses React Navigation

The export got past resolution and failed inside `@expo/router-server`. **No document specifies
`web.output`** — it was a P12 choice — so this is X-28, corrected to `"single"`, which is what a
React Navigation app on web is. Worth noting because a P12 agent used the `"static"` value to
justify passing `useSyncExternalStore`'s server-snapshot argument: the code is still right, the
reason given for it was not.

### 3. `MealCard` could not render a real meal

`Meal.imageUrl` is `string | null` — `contracts/core.ts` declares it, `mealSchema` validates it as
`httpUrl.nullable()` — and `MealCardProps.imageUrl` was `string`. **Every hand-written fixture in
P12's component suite chose a URL, so nothing failed.** This class of mismatch only surfaces where
real records meet a component, which is the tracer slice's whole purpose.

X-29, widened. The component already had the affordance: the image box is floored with
`card.skeleton`, which exists for "no image yet", and `component-contrast.test.ts` verifies the name
over the scrim over that fill at 6.85:1. So `null` renders the floor and no `Image` at all. The
alternative a caller would reach for — `imageUrl ?? ''` — type-checks and issues a request for the
empty URL, failing in the network log rather than in the types.

### 4. Half the CORS allowlist was missing its second spelling

The first e2e run put every data spec into "Working offline" while the screen itself was perfectly
correct. `corsOrigins` allowed both `localhost` and `127.0.0.1` for the API port and for 8081 —
**and only `localhost` for 19006.**

`localhost` and `127.0.0.1` are different origins to a browser, so an allowlist carrying one without
the other depends on how the developer happened to type the address. Derived from one list of ports
now, so a third port cannot arrive half-covered, and `boot.integration.test.ts` enumerates the pairs
in both directions — including that `127.0.0.1:4173` is still refused, so the fix did not widen into
"anything on the loopback".

The harness itself was also wrong: it served the export on 4173, an origin no document allows.
Serving it on 19006 is not a workaround — SDD §12 makes the deployment target the developer's own
machine served by Expo, and 19006 is the port Expo serves a web build on. **Widening the allowlist
to make a test pass would have loosened a real boundary for a harness's convenience.**

### 5. The export shipped 8.8 MB, and my own comment said it did not

`App.tsx` claimed that loading four faces avoids shipping the other fourteen Inter cuts. The export
disproved it: importing the four names **from the package barrel** still bundled all eighteen, since
the barrel `require`s every `.ttf` and Metro follows each one. Four subpath imports later, `dist` is
**4.2 MB** and carries exactly `Inter_400Regular`, `600SemiBold`, `700Bold`, `800ExtraBold` plus the
icon font. A 52% reduction, and the comment is now true.

## What was built, and the one assertion the phase exists for

- `features/catalog/ExploreScreen.tsx` — search, chips, list, and the three states TSD §6.8 names.
- `features/catalog/useMealSearch.ts` — the debounce and the abort.
- `features/catalog/exploreFilters.ts` — pure chip → `MealQuery` mapping.
- `features/register.ts` — the one module imported for its side effect (proposed S-row below).
- `infrastructure/api/ApiProvider.tsx` — the client, injected, because `screenFor` passes only
  `route` and `navigation` so there is no prop route in.
- `e2e/` — own `package.json` outside the workspaces, Playwright config with two `webServer`
  entries, a **dependency-free** static server in Node's `http`, and `specs/explore.spec.ts`.

**The abort matters more than the debounce, and it is not enough on its own.** A slow first request
landing after a fast second one renders the wrong results under the right search box. So the hook
has two guards, and they were probed **independently**:

| Guard removed                                      | Which test fails                                                           |
| -------------------------------------------------- | -------------------------------------------------------------------------- |
| the generation counter (abort left fully in place) | `does NOT render a slow first response that lands after a fast second one` |
| the `AbortController` (generation left in place)   | `aborts the superseded request rather than leaving it running`             |

The first probe is the one that matters: **with `abort()` still there, the stale response renders.**
`abort()` cannot un-resolve a promise whose continuation is already queued as a microtask, so the
newest-request check is what makes a stale render impossible rather than merely unlikely. That is
now evidence rather than a claim in a docblock.

## Two mistakes of mine in this phase

1. **My first search spec measured `FlatList`'s rendering budget, not the result set.** It compared
   `count()` before and after typing and failed with "Expected: not 8" — 8 being
   `initialNumToRender`. An unfiltered catalog of 60 and a search matching 12 both put 8 rows in the
   DOM, so the assertion could never have passed for the right reason. Every list assertion now
   compares the rendered meal **ids**. Recorded as **R-45**, because the failure mode is a test that
   looks like it is measuring the feature.
2. **My first six specs assumed `/` was Explore.** All twelve failed. The app opens on `HomeTab`,
   and at P13 only `Explore` is registered — so `/` correctly rendered `PlaceholderScreen`, and the
   accessibility snapshot from that failure is the proof the app was working rather than broken.
   The specs now tap the Explore tab, which is the path a user takes.

Also: the import scanner failed on its own docblock, which quoted two example specifiers. Comments
are blanked character-for-character before scanning now, so line numbers still point at the real
line — and the fixture in its self-check is assembled rather than written, because a regex cannot
tell a specifier in code from one inside a string.

## Known limitations carried forward

- **R-44 — web deep linking does not work.** `/explore?query=chicken` lands on Home.
  `routes.test.ts` and `linking.dom.test.ts` both pass, because `getStateFromPath` parses the path
  correctly in isolation; the wiring between the browser's URL and that parse is missing. **The
  cause is not identified** — adding `window.location.origin` to `linking.prefixes` was the obvious
  candidate, changed nothing, and the probe was reverted rather than left in. T-22-01 and T-22-02
  own this, and the spec is `test.fixme` so it turns back on when they fix it instead of being
  deleted and forgotten.
- **The e2e suite needs a 114 MB Chromium download**, outside the repo in Playwright's cache, and
  `@playwright/test` resolved to 1.63.0 against TSD §2.1's `^1.59.1` — the one caret range in the
  dependency table. Both recorded rather than assumed.
- **`ErrorState`'s retry re-mounts by identity** (`setFilters((c) => ({ ...c }))`), because nudging
  `search` through its own value is a no-op. It works and it is oblique; a dedicated `reload` nonce
  in the hook would be clearer if a second screen needs one.
- Nine routes still render `PlaceholderScreen`. That is the registry working, and each is one line
  in `features/register.ts` as P14–P21 land.

## Blockers

None. P14 has what it needs: a registered screen to copy the shape from, a working `ApiProvider`, a
