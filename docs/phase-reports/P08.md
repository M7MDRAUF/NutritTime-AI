## What the independent verification changed

Three CRITICALs. **The first two were in code I wrote and the third was a test I wrote that proved
nothing**, which is the more useful finding of the two kinds.

### CRITICAL - the server bound every interface, not localhost

`app.listen(config.PORT, cb)` with no host binds `0.0.0.0`. Confirmed with `netstat`:
`TCP 0.0.0.0:4967 LISTENING`.

That is not cosmetic. **TSD 2.1 drops `helmet` and `express-rate-limit` with the reason "the server
binds to localhost for one user (SDD 12)"**, SDD 12 opens "the threat surface is small: a local
server", and PRD 10.3 promises the user that their question and preferences "go only to a server on
the same machine". The mitigating control those three documents rely on was absent while the two
defences it waived were also absent - so on any shared network the API, and at P21 the chat endpoint
carrying questions and allergy lists, was reachable from the LAN.

Now `LISTEN_HOST = '127.0.0.1'`, the boot line records the host it bound, and a test connects on
loopback to prove it rather than trusting the constant.

### CRITICAL - the process reported "listening" when it had not got the port, and kept running

No `error` listener was attached to the server. Node reports a taken port as an **event**, not a
throw, so with a squatter holding the port the real entry point printed
`{"message":"listening","port":4981,...}`, **kept running while the other process answered every
request**, and a second real instance then exited **0**. The only signal an operator got was a lie -
the exact failure TSD 5.1 exists to prevent.

Now `server.on('error', ...)` exits non-zero naming the port. One residual: on Windows the
`listening` callback fires before the late `EADDRINUSE`, so a success line can still precede the
refusal. The exit code and the reason are deterministic and are what the test asserts; the ordering
is the platform's.

### CRITICAL - a test of mine asserted nothing, and it was the privacy guard

```ts
try {
  loadConfig({ OLLAMA_BASE_URL: 'http://user:hunter2@host/' });
  expect.unreachable('expected a ConfigError');
} catch (error) {
  /* assert on error.message */
}
```

Two faults compounding. A URL with embedded credentials **is a valid URL**, so nothing threw; then
`expect.unreachable`'s own throw was caught by the very `catch` that asserted on it, so the assertion
ran against `"expected \"expected a ConfigError\" not to be reached"` and passed. The guard against a
credential leaking into a config error message was completely unverified.

Replaced with a `messageFromThrow` helper that asserts a throw happened and that it was a
`ConfigError`, driven by an input that actually fails. **The same `try`/`expect.unreachable`/`catch`
shape appeared in four other places** and was sound only because those calls happen to throw - one
behaviour change from vacuous. All rewritten.

## Other defects fixed

1. **MAJOR - `OLLAMA_BASE_URL` accepted anything `new URL()` parses.** `javascript:alert(1)`,
   `file:///C:/secret`, `mailto:` and - most likely of all - a **dropped scheme** (`localhost:11434`)
   all booted clean. Every model call would then fail at P19 as `ai_unavailable`, which is the
   opposite of the boot refusal TSD 5.1 step 1 promises. Now http/https only. The refine is
   deliberately defensive because **Zod 4 runs a `.refine` even after an earlier check in the chain
   has failed**, so a bare `new URL()` there threw a raw `TypeError` out of `loadConfig`.
2. **MAJOR - a body-parser failure produced ZERO log lines.** `express.json` sat at position 2 and
   the logger at position 3; a parser error calls `next(err)`, Express skips every remaining
   non-error middleware, and the `finish` listener was never registered. An oversized body, malformed
   JSON and a bad charset each returned 400 and logged nothing, while TSD 5.8 and SDD 13 both promise
   one line per request - and `app.ts`'s own header comment named this exact failure. **The logger is
   now registered before the parser**, a deliberate departure from 5.3's numbering that weakens
   nothing in its rationale: the reason the cap must precede the routes is that a cap applied after
   parsing is not a cap, and the logger reads nothing from the body.
3. **MAJOR - any body-parser error that was not 413 or `SyntaxError`+400 became a 500.** A
   `Content-Encoding: gzip` header with a non-gzip body answered `500 internal_error` at log level
   `error` - a malformed request reported as a server fault, producible by any client at will. Now
   classified on the **status**: any 4xx is `invalid_request`.
4. **MAJOR - the 500 log line bypassed `logging.ts` and carried upstream text.** It wrote
   `error.stack`, message included, so zlib's `"incorrect header check"` was logged verbatim - and
   `String(error)` on an unknown throw would put anything at all in the line. `logging.ts` claimed
   the PRD 15.5 rule was kept structurally because "this module has no parameter through which any of
   them could arrive"; the claim was false, because `app.ts` wrote to the sink directly. Now
   `errorLogLine` takes only the error's **name** and its **stack frames with the message line
   stripped**, and the claim is true.
5. **MAJOR - `detailsFromIssues` reflected a submitted key into a response body.** Its own comment
   said "only the PATHS and Zod's own messages - never the submitted values", but Zod's
   `unrecognized_keys` message **is** a submitted value: `Unrecognized key: "peanut"`. Messages are
   now chosen here by issue code, and the only thing taken from an issue is its path. The test was
   passing a hand-typed lowercase stand-in and so never saw the real message; it is now driven by a
   real `chatRequestSchema.safeParse` result.
6. **MAJOR - the invalid-catalog PROCESS refusal was never tested,** and the `describe` said it was.
   The one test called `buildCatalog` in-process. T-08-09, its acceptance row, Plan 19.4 and TSD 8.3
   all ask for the exit code. Now proved through a fixture that boots the real `bootstrap()` over six
   deliberately broken catalogs - field failure, empty, not-an-array, duplicate id, mixed version,
   and superRefine-only - each asserting a non-zero exit, the record index, the field path, and that
   **no record content is echoed**.
7. **MAJOR - nothing in the suite observed a log line the server actually writes.** Every case passed
   `sink: () => undefined` and `logging.test.ts` exercised only the pure serialiser, which is why
   defects 2 and 4 lived here unseen. Added a capturing-sink suite: exactly one line per served
   request, **exactly one for a rejected body**, the route template never the concrete path, and no
   upstream message anywhere.
8. **MINOR - `/api/v1/meals` matched without its trailing slash**, so `GET /api/v1/mealsXYZ` answered
   `meal_not_found` - claiming a meal was missing on a path that names none.
9. **MINOR - `z.coerce.number()` is `Number()`,** so `PORT=0b111` booted on port 7 and `4e3` on 4000.
   Both in range, so the TSD row was satisfied while the operator got a port they did not type.
   Decimal digits only now, after a trim.
10. **MINOR - dead code and an unsafe export.** An unreachable empty-catalog branch; `configSchema`
    exported with no consumer; and `index.ts` both exported `bootstrap` **and** called it, so any
    `import './index.js'` started a listening server as a side effect. It now boots only when it is
    the process entry point - which is also what made defect 6's test possible.
11. **MINOR - coverage the TSD table demanded.** The explanation timeout's inclusive edges, `AI_FAKE`
    independent of `AI_ENABLED`, a disallowed CORS origin, and `GENERATION`'s four values - which had
    no assertion anywhere, so a mistyped `numPredict` would have shipped silently to P19.
12. **MINOR - four test names claimed more than their bodies checked.** "even when constructed after
    an upstream failure" had no upstream failure; "never submitted values" asserted
    `not.toContain('peanut')` on input containing no `peanut`.

## Divergences recorded, not resolved unilaterally

- **X-19 - the package graph.** TSD 2.3 and Plan 12.2 both say `server -> contracts, domain`, but
  TSD 5.1 step 2 requires the server to load and validate `meals.json`, which 7.1 exports from
  `@nutritime/catalog`. Resolved toward the more specific instruction, exactly as X-16 was, and
  recorded rather than left silent - SQG-04 is one of this phase's gate criteria.
- **X-20 - `internal_error` is a sixth wire code.** TSD 3.5 says "five codes, no more"; 5.3 step 6
  demands a 500 body and none of the five describes an unexpected throw. `INTERNAL_ERROR_BODY` is
  declared separately so the five-code union is not widened, but the emitted body does not satisfy
  the declared contract and P12's client must tolerate it.
- **Two type packages TSD 2.1 does not pin.** `@types/cors` and `@types/supertest`, because 2.1 pins
  `cors`, `supertest` **and** `@types/express` while omitting the first two's types - an asymmetry
  with no reading under which it is deliberate. The verifier agreed the reasoning holds and pointed
  out it applies equally to `@types/node`, which was reached only transitively; now declared.

## Known limitations carried forward

- **R-27 - the build artefact cannot boot.** `build:server` emits, but `node dist/index.js` fails
  `ERR_MODULE_NOT_FOUND`: the emitted `@nutritime/*` specifiers resolve to each package's `main`,
  which is uncompiled TypeScript. The fix needs project references **and** a `main` pointing at
  emitted JavaScript, which changes how vitest and tsx resolve every package - too wide to do inside
  P08 without risking every earlier phase's gate. Plan 21.3's "boot the artefact and call /health"
  is owed at **P26**. Nothing before P21 needs it; `dev:server` runs through `tsx`.
- **R-28 - three copies of zod resolve,** one of them 4.6.4 pulled transitively by
  `eslint-config-expo`. Both production paths get the 4.5.4 pin and every consumer reads issues
  structurally, so an `instanceof z.ZodError` across a package boundary is the hazard to avoid.
- **R-29 - the boot test is the second `process.env` reader,** against T-08-02's "exactly one file".
  A child process must inherit an ambient environment to be a realistic boot; every case sets what it
  depends on explicitly so an inherited `.env` cannot decide an outcome.
- **`express.json` caps only `application/json`,** so a large `text/plain` POST is unbounded. Literal
  to TSD 5.3, which specifies exactly `express.json({limit:'64kb'})`.
- **`request.route?.path` returns a router-relative path under a mounted `express.Router`,** losing
  the prefix. Correct at P08 with flat routes; a trap for P09 and P10, where
  `request.baseUrl + request.route.path` is the stable form.
