## The peanut test could not fail, and here is the arithmetic

T-15-07's acceptance is "peanut allergy → no peanut meal rendered". The first version used
`DEFAULT_PREFERENCES` — regular / balanced / medium — and asserted no peanut meal appeared in the
top three.

The catalog holds exactly two peanut-bearing meals. I recomputed the selected set with and without
the allergy at every period:

| period    | top three, no allergy                                                       | with `peanut` declared | identical |
| --------- | --------------------------------------------------------------------------- | ---------------------- | --------- |
| breakfast | english-breakfast, home-made-mandazi, full-english-breakfast                | same                   | **yes**   |
| lunch     | broccoli-stilton-soup, cajun-spiced-fish-tacos, mediterranean-pasta-salad   | same                   | **yes**   |
| dinner    | honey-teriyaki-salmon, chicken-enchilada-casserole, cajun-spiced-fish-tacos | same                   | **yes**   |
| snack     | home-made-mandazi, chocolate-gateau, eton-mess                              | same                   | **yes**   |

`pad-see-ew` ranks **4th of 60** at lunch and `rocky-road-fudge` **6th** at snack. **Deleting the
allergen hard-rejection entirely left the test green at every time of day.** It held by luck of the
scoring, not by the rule.

`budget: 'low'` at lunch is the lever that makes the rejection observable — it puts `pad-see-ew`
_into_ the top three, where removing it is something the DOM can see:

|                   | top three                                                               |
| ----------------- | ----------------------------------------------------------------------- |
| no allergy        | broccoli-stilton-soup, mediterranean-pasta-salad, **pad-see-ew**        |
| `peanut` declared | broccoli-stilton-soup, mediterranean-pasta-salad, spicy-arrabiata-penne |

The test now has a **control** — it asserts a peanut meal _is_ reachable first, so absence means
something — and a non-emptiness guard, because a failed request would empty the list and satisfy
every exclusion loop. **Probed:** disabling the hard rejection in `scoring.ts` now fails it with
`expected [ 'broccoli-stilton-soup', …(2) ] to not include 'pad-see-ew'`.

The e2e spec reads the peanut ids **from the server** rather than a fixture, so it cannot be
invalidated by a catalog change and fails loudly if the catalog stops having any.

## FR-003, and why the interval is the requirement

"Changing allergies **discards** the recommendations currently on screen." A screen that replaced
its list when the new response arrived would satisfy a careless reading and still leave a peanut meal
visible to someone who has just declared a peanut allergy — for a round trip, and **for ever if the
request failed**.

So `useRecommendations` sets `pending` synchronously at the top of the effect, before the request
goes out, keyed on `allergiesRevision`. The test holds the second response open — the stub never
resolves it — and asserts the old meals are _already gone_.

**Probed:** changing the hook to clear on response instead fails it, naming the meals still on
screen. And the no-op half was itself decoration until verification: comparing the rendered list
could not fail, because the stub resolves synchronously with the same three meals either way. It
counts **requests** now.

## The clock was frozen for the life of the process

`useRecommendations` memoised the period on `mealTimes` alone, defended by a comment I wrote:
_"A remount is when the time is re-read, which is when the user came back to the screen."_

**That was factually wrong.** A bottom-tab screen is not remounted on re-focus — `TabNavigator` sets
no `unmountOnBlur` — and nothing in the app read `AppState` or `useFocusEffect`. An app opened at
12:00 and resumed at 20:00 still said "Lunch" and still recommended lunch. That is P15's whole
objective and PRD FR-004.

The clock is now re-read on the two events that mean "the user is looking at this now": the screen
gaining focus, and the app returning to the foreground. Not on a timer — a screen that reclassified
itself every minute would swap the list out from under someone reading it at 10:30, which is the case
the original comment was right to guard against.

`useFocusEffect` needs a route context, so the focus half lives in `HomeScreenWithFocus` (what the
registry registers) and reaches the hook as a number. That keeps both the hook and the bare screen
testable without mounting a navigator — and the bug existed _because_ Home had only ever been tested
outside one.

**My first test for it was decoration too.** It called `render()` twice, building a fresh tree each
time, so the `useMemo` re-ran regardless of its dependency array — I probed it by restoring the old
array and the test still passed. It re-renders the **same root** now, because a re-focus does not
remount the screen; that is exactly why the bug existed.

## Three more tests that could not fail

- **The empty state was never reached.** The fixture (vegan + four allergens + low budget at lunch)
  returns **three** meals — I ran it — so the `if` was never taken and the `else` asserted the empty
  state was _absent_. `home-empty` was rendered by nothing in the suite, and T-15-05's "Empty …
  reachable" had no test. The stub now returns an empty response directly.
- **"At most three" for a requirement that says exactly three**, and "each with one reason" checked
  by finding the sentence once anywhere in the document. Both are counted per card now, and the
  screen slices to `MAX_RECOMMENDATIONS` so it cannot paint a fourth if a future response carries
  one.
- **The dom stub dropped `favoriteMealIds`**, passing `[]` instead of the request's list — unfaithful
  on exactly the field P10 uses to make the rejection observable (a favourited peanut meal must not
  buy its way past the filter), and it would have diverged silently at P16.

## Judgements recorded

- **S-46 — the disclaimer is above the meals**, and the test asserts the _order_, not merely the
  presence: a qualification a user scrolls past three cards to find has not qualified anything. It
  is `info` tone, not `warning` — dressing it as an error is how it becomes the thing users dismiss.
- **S-47 — only the fallback explanation is marked**, and on the card rather than in a legend.
  `explanationSource: 'fallback'` means no model saw that sentence, which is the interesting thing
  to name; marking both would badge every card and say nothing.
- **S-48 — `snack` reads as "Something small"**, because "Snack" is not a time of day.

## Known limitations carried forward

- **`favoriteMealIds` is hard-coded to `[]`.** P16 owns the favourites store; an empty list is a
  true statement about a user who has favourited nothing, not a placeholder. The stub now forwards
  whatever the request carries, so P16 changes one line.
- **R-45 — a DOM row count measures `initialNumToRender`, not a result set.** Every list assertion
  in this phase compares rendered ids.
- **R-35 — `allowFontScaling`, touch targets and the AI-progress timing are device-only.** The
  200 ms and 2 s thresholds are asserted as constants and through the state machine, not as elapsed
  time: a test that waited on a real timer would be slow and flaky, and one that faked the clock
  would assert against the fake.
- **T-15-04's AI-progress indicator is reachable only with `aiEnabled`**, and no model exists until
  P19 — so the copy ("Still writing your reasons…") has never been seen against a real explanation
  lane. P19 should look at it.
