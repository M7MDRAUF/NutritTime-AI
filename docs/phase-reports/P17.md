# P17 — Custom meal CRUD — Completion Report

The store, the validation, the Saved screen and the form through which a user authors their own
meals — and the phase where **the app asked for safety data, promised in writing to use it, and never
checked it.**

## How this window was built

P16, P17 and P18 were produced by **27 agents**: 11 writers, 13 read-only auditors and 3 end-to-end
engineers, plus the orchestrator's own integration.

`Plan.md` §4 permits two parallel writers here and §2 forbids manufacturing parallelism the
dependency graph does not allow. Twenty-seven agents were reconciled with that rule rather than
around it, by three devices:

1. **A per-agent write allowlist, with the shared spine reserved to the orchestrator.** `App.tsx`,
   `features/register.ts`, all of `navigation/**`, `shared/components/**`, `createStore.tsx` and all
   four documents were off limits to every agent — precisely the files several agents legitimately
   needed, and therefore precisely the files a naive fan-out corrupts. **`git status` showed zero
   tracked files modified outside an allowlist at every wave boundary.**
2. **Contract-first.** Every new module's public API was pinned before anyone wrote a line, so four
   screen agents coded against three stores that did not yet exist. That is what converts a
   dependency chain into a wave.
3. **Reports as files, in a fixed schema with `SEVERITY:` lines** — 27 agents triaged by grep rather
   than by reading 27 essays. There were **27 `NEEDS-INTEGRATION` items**; an auditor checked them
   off (20 applied, 5 consciously declined, 2 missed — one being a decision that existed only in a
   message to an agent and nowhere durable).

## What verification found

### CRITICAL — the custom-meal allergen field was a false safety promise

**V6.** The journey needs no unusual state: a user ticks **peanut** in Dietary Setup, then authors a
recipe containing "Peanut butter" and ticks allergen **peanut** under a caption reading _"Used to
keep this meal away from anyone with that allergy."_ Then —

- the "Your own recipes" row showed no marker (`MealCard` has no conflict prop, and nothing in its
  accessible name);
- tapping it opens **`MealForm`, not `MealDetails`** — an orchestrator routing decision;
- so the app's **only** caller of `conflictingAllergens` was _structurally unreachable_ for a custom
  meal;
- and nothing anywhere read `CustomMeal.allergenTags`. V6 probed the domain: it **would** have
  returned `['peanut']`. It was simply never asked.

**The cause was a decision that was correct in isolation.** Routing a custom meal to the form was
reasoned from TSD §6.8 — `MealDetails` is given `GET /meals/:id`, a custom meal has a UUID the server
has never heard of, and sending it there would make "not-found" mean two different things. What the
reasoning never asked was **which guarantees the routing choice took with it**. Recorded as **S-49**,
because the general lesson is more valuable than the fix: a locally-correct decision can delete a
safety property, and the question to ask of any routing choice is what surfaces it removes.

Fixed where a user actually meets a custom meal: the Saved row carries a domain-backed conflict
marker (both sections — **S-50**), and the form shows the notice while the meal is being authored.
The caption no longer promises filtering that cannot happen, since custom meals are not in the
recommendation set at all. Every conflict fixture reaches its conflict **by inference from an
ingredient name with the tag stripped**, plus a vacuity control asserting a tag filter misses it — so
the mutation that left P16's suite 24-of-25 green fails four tests here.

### CRITICAL — a save into an unreadable key reported success

**V2.** When `multiGet` throws, the repository marks every key `unavailable` with `[]` as the value,
and `createStore` then correctly **skips the write** — TSD §6.3's rule protecting bytes it cannot
read. But silently: `saveError` stays null and `saveBlocked` stays false. So Saved said "You have not
written any recipes yet", the user authored a meal, the confirmation reported success, `goBack()`
fired, the meal appeared in the list — **and nothing was ever written.** Gone at the next launch.

**Part of the cause was an orchestrator instruction.** The form was told to "confirm the write landed
by checking `hasCustomMeal` on the next rendered value". That confirms the **dispatch** landed, not
the write — the right check for the three reducer-level refusals it was written for, and worthless
for the storage layer, which is exactly the state where the user most needs to be told.

Both screens now read `entryStatus`, and the form **refuses the save outright** rather than warning:
an in-memory record nobody can write would show in Saved for the session and vanish at launch.

Two agents independently corrected the test lever: `failOn('getItem')` **cannot reach this state**,
because hydration is one `multiGet` and no store calls `repository.get()`. Recorded as **R-57**,
along with the consequence that the failure is all six keys at once — which makes it more severe, not
less.

### The highest-stakes question in P17, answered by fuzzing rather than argument

Can the form build a record `customMealSchema` rejects? That is P14's CRITICAL class, and here the
blast radius is every custom meal the user has authored, lost at a launch they cannot connect to the
cause.

**V2 ran a 40,000-draft differential fuzz plus 16 directed edge cases against an esbuild bundle of
the real modules: zero mismatches, zero schema rejections.** It then walked every `mealObjectSchema`
field independently to confirm the twelve-row agreement list was complete. The class is closed for
custom meals, and closed by measurement.

W5's probe pairing shows why the _validator_ rather than the backstop is what matters: deleting the
all-or-nothing rule produced 30 failures; deleting it **and** bypassing the schema backstop produced 32. A backstop that silently compensates for a missing validator is how a form comes to reject a meal
with no field to point at.

### MAJOR — a store suite whose eight identity assertions could not fail

**V9** probed `customMealsState.test.ts` with a resolve-time module swap: a reducer mutating in place
and returning `state` from **every** branch scored **26 of 26**. The same mutant against `favorites`
fails 14, because that suite carries a control set.

**This was an orchestrator process failure.** After W1 showed that identity assertions are
meaningless without a control, the requirement was written into the contracts file — into the section
for the store that already had one, and never sent to the two agents that had already finished.
Recording a rule is not enforcing it.

The fix went further than the standard it restored. `not.toBe(state)` alone is beatable by a mutant
that mutates in place and returns a fresh wrapper, so each control case now carries three assertions:
the state reference, the inner array reference, and that the input's field values are unchanged
afterwards. V9's mutant now scores 26 of 30, all four failures in the control set.

### MAJOR — an unhandled synchronous throw could hang the favourites section for ever

**V8.** `favoritesFeed.ts` had an async IIFE with no `catch`, while its sibling `useMealDetails.ts`
wraps the identical call and states why: `getMeal` throws **synchronously** before returning a
promise, because `mealPath` runs `encodeURIComponent`, which throws `URIError` on a lone surrogate. A
favourite id survives only a non-empty-string check, so a corrupt store reaches it. Same shape as the
protected lane, minus the protection.

### MAJOR — an orphaned favourite could vanish without explanation

**V2 and V12** both found `saved-favorites-unresolved` rendered by no test in the repository:
deleting the element left the suite green, and a favourite whose fetch failed for a **non-404** reason
then disappeared silently — the defining clause of the screen's own orphan design. Covered now,
including the non-404 path. The orphan row's "Remove from favourites" also gained a confirmation:
**V10** pointed out that for an orphan the removal is irreversible, since no screen can reach a 404'd
record to re-favourite it.

### The mutation audit, run last and alone

The twenty-seventh agent existed to answer `Plan.md` §6.1's question mechanically: **41 mutations,
of which 9 produced zero failures.** It ran alone because it is the only agent permitted to patch
production code, and an earlier agent's probe driver had already crashed between writing a patch and
restoring it — the three phantom typecheck errors that followed cost another agent a round. It
confirmed the tree restored against recorded SHA-256 baselines after every individual restore and
twice at the end.

**Its worst finding was on the orchestrator's own test.** Giving `registerScreens()` an unconditional
early `return` — which drops **every screen in the app** to `PlaceholderScreen` — left all 2012 tests
green, because that test read `register.ts` as _source text_ and regex-matched the calls without ever
executing the function. It is the exact defect the file's docstring claimed it was written to catch.
Replaced with a `.dom` test that calls `registerScreens()` and asserts the **specific component**
bound to each route through a new `registeredScreen()` introspection export — `screenFor` cannot
answer the question, because it returns its stable wrapper whether or not anything is registered
behind it. Probed against both of V4's mutations: the early return now fails 4 tests, and binding
`Splash` to the wrong component fails 2.

It also found that **Home's "your preferences were reset" banner was deletable in silence** — the one
reset a user must be told about, since a quarantined profile means `allergies` is `[]`, every meal
passes the filter, and the app looks entirely normal. Now covered, reached the way the app reaches it
(a well-formed envelope with an invalid value), and the test's own second assertion **failed first
and re-derived R-54**: the read path does remove the key, and the mount projection writes the
defaults straight back a tick later.

Of the remaining zero-failure mutations, four are in `App.tsx`, which has **no behavioural unit
test** — three suites replicate its provider tree rather than importing it. The e2e suite covers the
worst of them: hoisting a store provider above `DataResetProvider` would throw at boot, so every
spec would fail. Recorded rather than fixed, with that reasoning. Two are the `MAX_*` bound
tautologies, latent because both bounds are 200.

## Judgements recorded

**S-49** (where a custom meal opens, and what that cost), **S-50** (Saved marks, Explore does not),
**S-57** (where a UUID comes from with no `uuid` dependency and no `crypto` on Hermes), and **X-33** —
`favorites` de-duplicates in `create` where TSD §6.3 prints otherwise, and `customMeals` deliberately
does not. That asymmetry is right, and the argument is worth keeping verbatim:

> `favorites` holds **ids**, where `['a','a']` and `['a']` denote the same set and the duplicate
> carries no information. `customMeals` holds **records** — two entries under one id are two distinct
> authored meals that happen to share it. De-duplicating in `create` would silently delete a meal the
> user wrote, at hydration: P14's defect class. The React-key cost is a display defect payable by the
> renderer; data loss is not payable at all.

`SavedScreen` pays that cost by keying on `index:id`, with the reasoning at the site.

## Known limitations carried forward

- **`MealFormScreen.tsx` is 892 lines** — thirteen `FormField` call sites plus the four things that
  must not be separated (draft state, the validator call, S-43's visited-field filter, the
  create-confirmation lane). One extraction already happened. §17.1 carries the row and **flags it
  for a dedicated pass rather than accepting it as final**.
- **R-58 — three copies of the store-failure presentation** (`DietarySetupScreen`, `MealFormScreen`,
  `SettingsScreen`). Three copies are how two screens come to disagree about whether a failed write
  was reported. The shared home is beside `StoreStatus` in `state/`, not `shared/components/`, whose
  inventory TSD §6.7 caps at sixteen.
- **A refused create is silent on all three paths** (bound, duplicate id, schema). The callers check
  before dispatching and confirm afterwards; each refusal now carries an unreachability assertion
  rather than a comment, so the claim fails loudly if an upstream guard weakens.
- **`customMeals` appends**, so the "newest 200 survive" reasoning that holds for favourites is
  **false** here: a truncating read would cost the user their newest recipes. Reachable only through
  legacy data or an import, since the reducer refuses the 201st.
- **X-32** — TSD §9 and `Plan.md` §18 both name `features/saved-meals/MealForm`; the code is at
  `features/saved/`. Raised for the user.
