## 2. The row that does not describe this architecture

T-25-02 asks for "local navigation, search and filtering ≤ 150 ms", with "over the meals already
loaded" doing the work. **Navigation is local and passes at 13 ms. Search and filtering are not
local** — they go to the server — so the row as written describes an architecture
`exploreFilters.ts` does not implement, and no target is asserted for those two. Recorded as a
divergence rather than measured against a figure that does not apply.

**And a real defect fell out of it: a filter chip pays the 300 ms text debounce.** Measured 30.7 ms
with an empty search box against **330.9 ms** with text in it — while `useMealSearch.ts`'s own
docstring claims filter changes fire immediately. That is a §6.1j comment defect sitting on top of a
user-visible one, and it is the difference between passing and failing §10.1's 150 ms for anyone who
has typed.

## 3. X-48 — two PRD §10.1 rows that cannot both hold, and a PASS measured with no model

§10.1 asks for "app start to usable Home **≤ 2.5 s**" and "recommendation explanation, warm model
**~5 s**". `recommendations.ts` **awaits `explain()` for each of the three selected meals,
sequentially, before `response.json(body)`**, and `definitions.ts` ships `aiEnabled: true` — so
that is the **default** path, not an opt-in.

The 204.1 ms PASS above is correct **for this machine**, where no model exists and the explanation
lane fails fast into fallback text. With a warm model at §10.1's own ~5 s each, three sequential
explanations exceed both the 2.5 s row and the 12 s deadline.

**The ambiguity is what "usable Home" means**, and the two readings give opposite verdicts: if it is
"the screen is interactive and showing its computed meal period" — which P15 renders **before any
request**, deliberately, so the screen is never blank while it waits — then 2.5 s holds and the cards
arriving later is the design. If it is "the three recommendations are readable", the shipped default
cannot meet it with a model running. **Recorded for a ruling; the target is not relaxed**, and the
figure above should be read as _"with AI unavailable"_ whichever way it is decided.

## 4. T-25-05 — three of PRD §10.1's four claims

§10.1, verbatim: _"A cold model load takes roughly a minute and will exceed the assistant's timeout.
The first request after a restart may legitimately fail and then recover on its own. The UI shows a
loading state after 200 ms and an AI-progress message after 2 s."_

Met and measured: the first request **503s**; a later request **recovers with no user action beyond
retrying**; the 503 is a **temporary-condition** message with a working retry and **no upstream
string** (PRD §12 and TSD §3.5 — a user-facing error is fixed local copy). The fourth claim — a real
~60 s cold load — is **not reachable here** and was not simulated and called a measurement.

**The UI half was separately found missing and then built** (see `P23.md` §4): the assistant
implemented **neither** threshold, so a cold question showed one static sentence for up to the full
30 s. The constants existed in exactly one place, `features/home/useRecommendations.ts`.

## 5. T-25-06 — failure injection, and the probe that earned its keep

All three named modes plus a fourth were measured against the **existing** coverage first, and
**none measured "none"**: Ollama stopped 12, `ai_busy` 5, corrupt storage 13 of 219, app-side
unreachable 1 of 219. So the row was extended rather than duplicated, as it asks.

The new integration file is the **first pin at that layer** for three chat-lane properties:
lane-free-after-timeout (the probe reddened 11 explanation-lane tests and **zero** chat tests), a
truncated reply reaching the route, and a question appended to a log line.

**And the probe worth keeping is one that returned an inert zero.** The citation guard from P24 §7
was re-keyed from `resolved.namedMeals` to `reply.answered` — the version the design explicitly
forbids — and **45 of 45 tests still passed**. The guard's _effect_ was pinned; its _shape_ was not.
That zero named the discriminating case, which is a reply that cites nothing **and** claims it did
not answer: keyed on our data it is discarded, keyed on the model's flag it becomes a 200 carrying
the model's prose with **no citations at all**. That case now has a test, and the same mutation
reddens exactly it.

**Two probes in a row returned an inert zero and both were worth more than a redness** — this one and
the `SavedScreen` section keys, where removing both keys left the suite at **41 passed / 41 passed**.
The distinction §6.1k exists for — a zero meaning "nothing pins this" versus "my mutation was inert"
— is why each had to be run twice.

## 6. A MINOR that was a gate hole

`e2e/tsconfig.json` omitted `e2e/perf/**`, so this phase's fifteen-file harness was **linted but not
typechecked** by `npm run check` — and it hid a real type error until the author found it by hand.

**The include list had already failed this way once**, and that file's own comment records it: a
`support/**` module no spec imported was outside the program, ESLint saw it and `tsc -p e2e` did not.
The response then was to name the directory, which fixed that case and left the mechanism intact. So
the list is now gone — `include: ["**/*.ts"]` with an `exclude` naming only installed packages and
Playwright's two generated directories. **A directory cannot be forgotten if nothing has to remember
it**, which is the same reasoning that replaced the hand-listed denied-claim sweep with a walk.
`tsc -p e2e` now sees **13** files under `e2e/perf/` and is clean.
