## 3. T-24-03 — the **and**, and why the two surfaces assert opposite things

Acceptance: _"Peanut allergy excludes from Home **and** Explore"_. The **and** is the whole row, and
the two halves are deliberately different claims:

- **Home**: the conflicting meal is **absent** from the three recommendations.
- **Explore**: the meal is **present** — Explore lists the whole catalogue by design — and opening it
  **names the allergen**.

A spec asserting absence on Explore would be asserting a defect as the design. **And the probe that
proves the Explore half is not the server's:** blanking `conflictingAllergens` in the _web bundle_
reddens the notice (`meal-details-allergen-conflict … element(s) not found`), because that notice is
computed **on the device** — a server-only mutation misses it entirely, while Explore's listing
claim correctly stays green.

One earlier probe **passed because the app requests `localhost:4000` and the mutation targeted
`127.0.0.1:4000`** — an inert mutation, now fatal by assertion. That is §6.1k caught in the act.

**A MAJOR this row surfaced:** `ExploreScreen.tsx` carries no FR-007 disclaimer and `MealCard.tsx`
has no allergen prop, so a peanut-allergic user searching Explore sees a conflicting meal as an
ordinary card with **no caution of any kind** until they open it. Not ruled CRITICAL: the detail
screen names the conflict before any decision, Explore asserts nothing false, and no document
requires a row-level notice — the unmet requirement is PRD's **disclaimer**.

**And a document conflict, recorded not edited:** `TSD.md`'s "out of Explore" wording contradicts
the shipped design _and_ the higher document. PRD's FR-007/FR-010/FR-011 back the code; the route has
no `allergies` parameter, Explore filters nothing by design, and the detail screen ships _"The
catalog lists every meal, which is how you reached it."_ TSD's wording is the defect.

## 4. T-24-04 / T-24-05 — mostly verification, and one safety property closed

Both specs existed. The job was to attack them: for each existing assertion, what change would make
it fail? **Five assertions could not be the assertion that reports the defect they guard.**

**The one that mattered: `CustomMeal.allergenTags` IS read** — at `SavedMealRow.tsx:70,81` and
`MealFormScreen.tsx:294,503` — so the P16–P18 CRITICAL, where a user could tick peanut on their own
recipe and nothing ever read it, is genuinely closed. **But no e2e spec asserted either surface**,
and the probe is the proof: writing `allergenTags: []` **passed all four pre-existing tests** while
silently removing the allergen warning from a user's own recipe after a restart. Now pinned from both
the disk side and the screen side.

**A MAJOR in the cancel path's guard:** the assertion _"the sheet is open, not confirmed"_ can never
report an early delete, because the sheet lives inside `existing === undefined ? null : …` — the
probe reddens two neighbouring lines instead. Reordering it would be **weaker** (the write is async),
so the rationale was rewritten at the site rather than the test reshuffled.

P18's own lesson was already satisfied here before this phase: the cancel path existed and the probe
proves it discriminates.

## 6. T-24-07 — a control made of three absences

## 7. A CRITICAL-adjacent finding this phase sent back to the server

**An empty `citedMealIds` passed all four containment checks**, so a resolved answer could ship with
`citations: []` while the meals it drew on sat in `resolved.namedMeals` — against PRD §7.3's _"Show
the meals the answer drew on as citations."_ Reachable against a real model, because TSD §5.5's
schema constrains citation **values** through an enum and says nothing about the array's minimum
length. **`AI_FAKE` cannot produce it** — its echo carries the domain's own citations by construction
— which is why nine phases of `AI_FAKE` evidence were consistent with the defect. Found by _reading_
the route, not by running it.

Fixed in the route rather than as a fifth check, so TSD §5.7's specified four stay four, and keyed on
`resolved.namedMeals` — our data — never on `reply.answered`, because `containReply`'s own docstring
warns that a check conditional on a boolean the model controls hands the model a switch for turning
containment off. See `P25.md` §5 for the probe that made the guard's _shape_ load-bearing. R-71
records the better-for-the-user alternative that was **not** built.

## 8. What could NOT be verified

- **The operator's `AI_ENABLED=false` path at the e2e layer.** The harness fixes `AI_FAKE=true` with
  no `AI_ENABLED` before the first spec runs, so only the **user's** switch is reachable — driven
  through the real Settings toggle. The operator path is covered at
  `chat.integration.test.ts:518` and `Assistant.dom.test.tsx:152`. **No 503 was faked to pretend
  otherwise.**
- **A real `gemma3:4b` pass.** Everything runs through `AI_FAKE`, which is a real server path and not
  a real model. Registered as a manual check before the final audit.
- **The bundle the specs measured is the built `dist/`, not current source** on any run where the
  export was not rebuilt first — stated because it bounds what an e2e green means.
- **Playwright runs must be exclusive.** Three agents independently produced false failures from
  harness contention — 15/18/3/2, then 14 of 28 and 6 of 28, all green on an immediate re-run alone.
  Cause: a shared `e2e/test-results` (no `outputDir`) and `reuseExistingServer` handing a spec a
  server another run is tearing down. **A red e2e number produced while another run is live is not
  evidence of anything.** The config fix is filed; it was deliberately not applied mid-wave, since
  changing the config under running agents is the very thing the rule forbids.
